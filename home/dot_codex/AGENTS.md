# User-Level Agent Rules

这些规则适用于我的所有 Codex 工作区。项目内 `AGENTS.md` 可以补充更具体的规则，但不要削弱这里的约束。

## 先定标准，再下结论

做分析、调研、方案比较、故障归因、代码审查或风险判断时，不允许先预设结论再寻找支撑材料。开始收集和解释证据前，只能先定义问题、证据标准、参考源优先级和最终报告格式。

开始前必须明确：

- 问题：要回答什么，目标语义是什么，哪些问题不在本次范围内。
- 证据标准：什么证据足以支持、削弱或推翻一个判断。
- 参考源优先级：优先使用当前仓库、可复现实验、运行结果、官方 / 上游文档和一手记录；二手总结、经验判断或推测只能作为低优先级线索。
- 报告格式：至少区分事实、证据、推理、结论、置信度和仍需验证的问题。

报告时必须把事实、观察、推理和结论分开写。证据不足时，应明确说“不足以得出结论”，列出缺口和下一步验证方式；不要用倾向性措辞、选择性引用或未经验证的假设把不确定性包装成结论。

## 标准原语优先

做架构设计、缺陷修复、重构或接入外部系统时，必须先定义目标语义，再选择能直接表达该语义的官方 / 上游 / 标准原语。

如果官方或上游已经提供了能够覆盖目标语义的一等原语，不允许为了“稳妥”保留本地 workaround、旧路径或自研兜底，除非能用当前仓库或运行环境中的具体证据说明该 fallback 必不可少。

提出或保留 fallback 前，必须先回答：

- 这个 fallback 对应的生产条件是什么？
- 这个条件是否能在当前仓库、部署拓扑或运行时中被观察到？
- 上游是否已经提供了更贴近语义的一等原语？
- 这个 fallback 是否会掩盖 race、语义错配、所有权不清或测试缺口？

如果答案没有证据支撑，应删除旧路径，使用能直接表达目标语义的标准原语；不要给旧实现找台阶。

## 倾向充血模型和方法

做架构设计、重构或新增公共模块时，优先把行为放到能表达职责的模型方法上，而不是堆包级私有函数。

设计边界时必须先问：

- 这个行为属于哪个领域对象、运行器、加载器、解析器、报告对象或配置对象？
- 这个对象是否应该持有相关状态、缓存、输入事实或派生信息？
- 调用方读到方法名时，是否能直接理解行为归属？
- 如果把它写成包级私有函数，是否只是隐藏了一个本应命名的概念？

默认偏好：

- 用充血模型表达核心流程，例如 `Runner.Run`、`PackageLoader.Load`、`ModuleResolver.Resolve`、`Report.JSON`。
- 让对象负责自己的派生信息和展示形式，例如 `Module.GoMod`、`Module.Trace`、`Package.GoFiles`。
- 包级私有函数只适合非常局部、无领域含义、无状态的机械细节；一旦它承载扫描、解析、加载、转换、校验、报告或执行流程，就应该提升为模型方法。
- 不要为了“少暴露 API”把真实概念压成一串私有 helper。简单不是函数少，而是职责清楚。

## 一致性是交付标准

当移除、替换、废弃某个实现、协议、命令、字段、术语或架构路径时，必须把项目一致性作为交付标准的一部分。

完成代码改动前，必须做一致性扫尾：

1. 用 `rg` 全仓搜索被移除 / 替换的关键词、命令、函数名、配置名、注释术语和测试名。
2. 清理或更新仍引用旧路径的注释、文档、测试、fake / mock、fixture、脚本、错误信息、workflow、示例和设计说明。
3. 不允许留下“历史上这么叫”的测试名、注释或断言，除非它是在兼容性测试中明确验证旧输入。
4. 如果旧路径必须保留，必须写明保留原因、触发条件和验证方式。
5. 最终回复里说明一致性搜索使用了哪些关键词，以及是否还有刻意保留项。

优先级：项目一致性 > 局部最小改动。不要只让代码能编译，要让仓库表达同一套当前设计。

## 测试不要固化临时护栏

测试应验证稳定业务行为、公共契约、跨模块协作和已经决定长期维护的约束，不要把一次 review 里的临时风格检查直接固化成长期守护测试。

只固化实现形状、没有稳定行为价值的测试没有保留价值，必须完全避免；看见存量也要删除，而不是迁就、改名或继续维护。

这类测试包括但不限于：

- 只断言某个私有 helper、内部类型、文件布局、函数拆分、调用顺序或 mock 交互形状，但不验证可观察行为。
- 只为了防止本次重构漏改而检查命名、目录、注释、临时约定或迁移中间态。
- 只复制当前实现细节作为快照，却不能说明破坏它会造成什么用户可见行为、公共契约或长期工程约束的损失。
- 让未来合理重构必须先改测试，而不是通过行为回归来暴露真实风险。

遇到这类测试时，默认动作是删除。只有能明确说明其保护的是稳定业务行为、公共契约、跨模块协作或长期维护的工程约束，才允许把它改写成行为测试或 linter 规则；否则不要留下常驻测试。

处理风格、迁移或一致性问题时：

- 可以临时用 `rg`、脚本或一次性测试确认现状。
- 如果只是为了本次重构防止自己漏改，完成后应删除临时守护测试。
- 只有当规则本身已经成为长期产品 / 工程契约，并且未来破坏会造成真实风险时，才把它写成常驻测试或 linter 规则。
- 最终回复里说明临时检查使用了什么命令，以及是否没有留下常驻测试。
