# 严审开发

把主 Agent 当作编排者：只固定任务、调度 Agent、推进门禁和汇报结果，绝不直接修改代码。每轮都从原始需求、仓库和当前 diff 重建上下文，不依赖旧 Agent 的对话记忆。

若无法创建彼此隔离的全新 Agent，停止并说明限制；不得由主 Agent 模拟多个角色。

## 1. 固定任务

读取仓库规范和工作区现状，固定原始需求、验收标准、变更基线、任务范围及仓库规定的验证命令。
找出根目录与目标目录的 Agent 指令、目标文件适用的设计原则、编码规范、依赖规则、文档或变更记录
要求、格式化和生成规则、custom lint 规则以及 hook/CI 入口。保护既有修改，不把无关变更纳入任务。

完成标准：这些原始材料足以组成一份自包含的实现任务，并且每类预期修改的文件都有明确的规则
来源和验证入口。

## 2. 独立实现

创建一个 `fork_turns="none"` 的全新实现 Agent。只向它提供任务原始材料、当前仓库；返工轮次再提供本轮审查汇总和架构方案，不提供旧实现 Agent 的思考过程。实现 Agent 必须亲自完成工作，不得再委派或提前启动代码审查。

实现 Agent 不得立即修改文件。它必须先读完全部适用规则，补充仓库探索发现的嵌套指令或遗漏规则，
并向主 Agent 返回一份规范清单，逐项映射“目标文件或模块 → 规则来源 → 本次必须保持的约束 →
验证命令”。主 Agent 只有在确认每类预期修改均已覆盖后，才能让同一实现 Agent 开始修改。不得以
先写代码再根据 lint 报错试修代替规范理解。

要求实现 Agent：

- 先理解现有设计再修改；做小而完整的纵向变更，修根因，不做投机抽象或无关重构。
- 在稳定接口和测试缝处验证行为；保护兼容性、错误语义与现有用户修改。
- 修改完成后运行仓库要求的测试、类型检查和静态检查。
- 在送审前按仓库原生方式运行 pre-commit hook，直至通过；hook 产生的修改属于本轮实现，必须重新验证。

完成标准：规范清单门禁已通过，所有要求的检查和 pre-commit 均通过，待审 diff 已冻结。

## 3. 三人隔离审查

并行创建恰好三名 `fork_turns="none"` 的全新审查 Agent。三者只能看到原始需求与验收标准、冻结的 diff、仓库规范及原始验证结果；不得看到实现理由、历史审查、架构结论或彼此的意见。

三者都审查完整变更并投整体票，同时分别主审：

1. 正确性、边界条件、错误处理、并发和测试。
2. 安全、性能、资源管理、兼容性和运行风险。
3. 可维护性、接口契约、可读性、变更范围和回归风险。

每项问题必须给出文件与行号、严重程度、证据和可执行建议；每名审查者最终只能投“通过”或“要求修改”。主 Agent 只去重并汇总，不替审查者改写判断。

通过门禁：至少两票通过，且没有已确认的阻断问题。阻断问题只有在可复现，或被至少两名审查者独立发现时才算已确认。

完成标准：收到三份独立报告，并明确得出通过或返工结论。

## 4. 架构复盘

创建一个 `fork_turns="none"` 的全新架构设计师 Agent，向它提供任务、代码、冻结 diff 和三审汇总。它不修改代码、不参与投票，只负责：

- 按共同根因、设计约束和影响范围归类问题。
- 判断局部修复是否足够；若足够，明确理由。
- 若存在共性，给出最小的系统性方案、必须保持的设计不变量和验收条件，追求模块深度与修改局部性，拒绝症状式补丁。

门禁未通过时，把架构方案作为约束交给下一名全新实现 Agent，然后回到第 2 步。门禁已通过时，架构师的非阻断建议只进入最终报告，不构成第四张票。

完成标准：返工已有自包含方案，或通过结果已有架构确认。

## 5. 提交

确认当前 diff 与获批 diff 完全一致，只暂存本任务文件并默认创建原子提交。不得跳过 hook。若提交时 hook 失败或改变文件，本轮批准立即失效，回到第 2 步，重新验证和三审。

最终报告提交哈希、三票结果、架构结论、实际运行的验证命令及剩余风险。

完成标准：提交成功，pre-commit 通过，提交内容与获批 diff 一致。
