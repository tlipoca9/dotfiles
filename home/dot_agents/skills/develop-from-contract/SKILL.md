# 从契约开发

效率优先，但必须保持五个不变量：

1. 行为契约由用户明确批准，批准后冻结；
2. 契约层和实现层分别由全新的只读架构师完成架构设计；
3. 契约测试与生产实现由两轮上下文隔离的 `/develop` 分别交付；
4. 契约层先产生可信 RED，生产实现再使用相同的契约判定方法将其转为 GREEN；
5. 实现层不得修改冻结契约、契约测试或契约规定的判定方法。

主 Agent 负责编排、记录契约共识和执行阶段门禁。契约冻结前，主 Agent 只可修改非可执行契约文档；
生产代码、测试及其他可执行产物必须交给开发 subagent。

## 0. 分流并行工作

“主干需求”指触发本流程的用户需求；契约冻结后，以冻结契约及其验收标准为准。开发中发现的缺陷只有
同时满足以下条件，才定义为“独立修复任务”：

- 现有规范、既有测试或可复现证据足以唯一确定预期行为，不需要用户作出新的行为决定；
- 该缺陷不属于主干需求的交付范围，其失败或延期不影响主干需求通过验收；
- 授权写入路径与主干任务已经修改、正在修改或计划修改的路径不重叠，也不修改主干需求依赖的公共接口、
  schema、migration 或生成入口；
- 存在不依赖主干未完成代码的独立验证命令。

满足全部条件时，立即启动一个独立 subagent，向其提供问题证据、预期行为、授权写入路径、禁止写入范围
和验证命令；主 Agent 随即继续主干需求，不等待独立修复任务完成。用户把该缺陷加入本次交付范围时，
它立即成为主干需求的一部分；若仍满足第 0 节的模块并行条件，可作为主干并行模块交付，否则串行纳入主干。

上述任一条件不再成立时，立即停止该任务的并行修改。若主干验收依赖该修复，则将其纳入主干需求；
否则记录为后续任务。禁止两个 Agent 并发修改同一路径或共同定义尚未冻结的接口。

每轮开发默认由一个开发 subagent 交付一个完整、可验证的模块。只有至少两个模块可以同时开始、写入路径
互不重叠、各有独立验证命令，且需要修改的公共文件和接口均已指定唯一负责人时，才并行启动多个开发
subagent。第 2 节的架构师依据代码架构决定模块数量；即使最终只有一个模块，也不得省略架构设计。

完成标准：每项工作已归入主干需求、独立修复任务或后续任务；所有并行任务均满足上述条件。

## 1. 约定并冻结契约

先调查代码和项目规范。只有仍无法从现有证据确定、且不同答案会改变可观察行为的问题才运行
`/grilling`；按决策依赖顺序一次询问一个问题，并给出推荐答案。

使用仓库现有的契约表达方式；不存在既有方式时使用 Markdown，不引入新的 DSL。契约应对本次受影响的
可观察行为完整，对未受影响行为不展开。至少记录：

- 目标、非目标和对外入口；
- 输入校验、前置条件、权限、成功结果和错误语义；
- 可观察副作用，以及本次适用的原子性、幂等性、兼容性、异步、并发和故障语义；
- 带唯一稳定 ID 的验收标准；
- 每项验收标准的判定方法：自动化验收记录精确执行命令；人工验收记录操作步骤和预期观察结果。

每个受影响的对外入口都必须覆盖输入校验、返回结果和副作用。按仓库约定保存契约；没有约定时使用
`docs/contracts/<requirement-slug>.md`。向用户展示完整契约并等待明确批准。批准后，任何 Agent 都不得
自行补充、放宽或改变契约语义。

完成标准：不存在尚未决定且会改变可观察行为的问题；用户已明确批准契约；任意实现都可依据契约被判定
为合格或不合格。

## 2. 完成代码架构设计

在契约层和实现层各启动一名全新的只读架构师 Agent。两名架构师都必须亲自阅读冻结契约、当前代码、
适用项目规范和 `$codebase-design`；不得修改契约、代码、测试、schema、生成物或脚本。实现层架构师只可
获得原始需求、当前仓库、冻结契约和已提交的契约层产物，不得获得契约层 Agent 的思考、对话或审查历史。

架构师的首要产物是代码架构设计，subagent 分工只是架构设计的派生结果。架构师必须：

- 重建受影响代码的现状：模块、接口、seam、adapter、依赖方向、数据与控制流，以及必须保持的设计不变量；
- 设计目标架构：行为应归属哪个模块，接口和 seam 如何变化，依赖、状态、错误、并发和副作用如何流动；
- 追求深模块、小接口、变更局部性和可测试性，避免透传层、假想 seam、跨调用方复制逻辑或暴露内部细节；
- 当需求新增或改变跨模块接口、seam 或数据所有权时，比较至少两种实质不同的方案，并基于深度、局部性、
  可测试性、兼容性和实现复杂度明确推荐其中一种；
- 说明关键取舍、被否决方案、迁移或集成顺序、主要失败模式和验证策略；
- 最后才确定开发 subagent 数量，并为每个模块指定可验证结果、唯一负责人、写入路径、前置依赖和验证命令。

契约层架构师重点设计契约覆盖、黑盒测试 seam、测试侧 harness 和可信 RED 的形成方式。实现层架构师重点
设计生产模块、接口和 adapter 如何在不改变冻结契约测试的前提下实现全部行为。

没有目标架构、设计理由和不变量的任务拆分不是架构设计，主 Agent 不得据此派工。主 Agent 必须确认每项
验收标准都有明确的模块归属和测试 seam，且所有公共文件与接口都有唯一负责人。

完成标准：目标架构、现状到目标的变更、设计不变量、取舍、模块所有权、依赖顺序和验证方式均已明确；
开发任务可以从架构设计直接派生，而不是先分工再补架构理由。

## 3. 独立交付契约层

先由契约层架构师完成第 2 节，再按照经主 Agent 确认的架构设计运行第一次 `/develop`。只提供原始需求、
冻结契约和当前仓库状态；当前仓库状态包括当前 Git commit 与已有未提交变更。冻结契约文档只读；该轮
只可新增或修改黑盒契约测试，以及测试侧必需的 harness、协议或 schema，不得修改生产实现。

契约测试必须引用对应的稳定验收 ID。执行契约判定方法时，自动化验收必须因为目标行为尚未实现而出现
业务断言失败；人工验收必须观察到实际结果与契约预期不符。这种状态称为“可信 RED”。编译失败、依赖或
环境错误、测试代码错误都不是可信 RED。除预期失败的契约测试外，适用仓库规范要求的检查必须通过。

由 `/develop` 负责其内部的规范盘点、独立审查和原子提交，本 skill 不重复规定这些机制。

完成标准：每项验收标准均有契约测试或已记录的可重复人工检查；可信 RED 可重复；契约层已形成独立提交。

## 4. 独立交付实现层

先由实现层架构师独立完成第 2 节，再按照新的架构设计运行一次全新的 `/develop`。只提供原始需求、当前
仓库、冻结契约和已提交的契约层产物；不得提供契约层 Agent 的思考过程、对话或审查历史。

实现层可修改生产代码并增加实现侧测试，但冻结契约、契约测试及其判定方法只读。重新运行与契约层完全
相同的自动化命令和人工验收步骤，使可信 RED 转为 GREEN；同时通过适用仓库规范要求的回归测试、类型
检查、静态检查和 pre-commit。

完成标准：冻结契约的全部验收标准通过；实现层已形成第二个独立提交；两轮开发和审查的上下文彼此隔离。

## 5. 处理契约异议

“契约异议”指任何需要补充、删除、放宽或改变冻结契约语义或判定方法的问题。发现契约异议时，立即停止
所有结果依赖争议条款的工作；不依赖争议条款的任务可继续。任何 Agent 都不得自行修改冻结契约。

返回第 1 步，由用户重新决定并批准契约。契约一旦变化，本次需求已有的契约层和实现层验证结论全部失效，
从第 2 步重新设计并交付。

完成标准：冻结契约不存在未经用户批准的语义或判定方法变更。

## 6. 汇报

最终报告契约路径、验收标准与判定方法的对应关系、可信 RED → GREEN 证据、两轮 `/develop` 的提交和
审查结果、两轮架构设计及关键取舍、实际模块分工、实际运行的自动化命令和人工验收结果、独立修复任务
状态和剩余风险。

未完成的独立修复任务只报告当前状态和后续动作，不得宣称已经修复；因为它不属于主干契约，不能阻塞
主干需求的完成判定。
