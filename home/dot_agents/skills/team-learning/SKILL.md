# Team learning

Use the team root at /Users/tlipoca9/.codex/team. Identify your assigned role
from TEAM.md; the primary coordinator is rin. Each role may learn, maintain its
personal knowledge, and contribute shared knowledge within the current task's
authorization. A learner owns applying what they learn.

## Retrieve before learning

Read knowledge/personal/<role-id>/INDEX.md and knowledge/team/INDEX.md, then
follow the task-relevant branches. Each index points to content with a concrete
read condition. Stop when the task is supported. If routing misses a likely
topic, search the knowledge tree and improve the relevant pointer.

Consult the project's authoritative documents or relevant existing skill before
creating a new rule. Recheck sources for version-sensitive claims. Use focused
research or a discriminating experiment to fill a real gap. Keep raw output,
temporary scripts, and task-local notes outside product repositories and out
of the lasting knowledge tree.

## Assess and apply

Review feedback is a claim to evaluate. Check its premise and evidence; defend
a supported position with a counterexample or decisive check. Correct the work
and method when the finding is confirmed. Refuted feedback should improve the
reviewer's method. A disagreement alone creates no new rule.

Apply a discovery to the task where possible and verify its relevant effect.
Describe the actual evidence: source-supported, experimentally checked, or a
hypothesis. A local example establishes its own scope, not a universal law.

## Store what changes future decisions

Persist knowledge that has reusable value beyond this task. Choose the smallest
appropriate home: a personal technique, an existing shared topic, an existing
skill, or the project's authoritative documentation. Link to maintained source
material rather than copying manuals or maintaining duplicate project facts.

A useful entry contains the triggering situation, the actionable understanding,
its applicable scope, and evidence or source links. Add version/check date when
freshness matters, and counterexamples when they materially refine the rule.
Mark untested ideas as hypotheses. Keep the form proportional to the content;
see [entry examples](references/entries.md) when creating or splitting a topic.

Update an existing entry before creating a new one. Use lowercase descriptive
filenames. Add or repair the nearest index pointer in the same change, so a
future task can discover the content without this conversation. Split a branch
only when it contains distinct useful read conditions. Recursive indexing means
selective traversal, not loading every descendant. Keep parent-to-child index
traversal acyclic; cross-references can link to an already visited canonical
entry without loading it again. Check affected links after moving content.

## Contribute to team knowledge

Members may directly contribute clear, sourced facts or narrowly established
methods. Reuse the canonical topic and preserve its scope and evidence. When
replacing a disputed conclusion or a consequential shared working rule, ask a
relevant peer to inspect the evidence; 凛 coordinates unresolved tradeoffs.
Explicit user instructions and confirmed business decisions retain precedence.

For promotion, move reusable substance into knowledge/team/ and link to that
single entry from the author's personal index. Retain only genuinely personal
application notes. Give a subject an owner or contributor attribution when it
helps maintenance; all members may propose corrections.

Coordinate concurrent edits with the other writer. Reread the current file
before applying a focused patch and preserve other contributions. Shared index
changes use the same single-writer handoff as code. If the runtime cannot write
the knowledge store, return the proposed delta to 凛 and distinguish it from a
saved update.

## Reuse and revise

On the next relevant task, retrieve the entry and apply its check before peer
review. Evidence of growth is a better independent decision or earlier defect
detection. On recurrence, inspect whether retrieval failed, the rule was vague,
its scope changed, or it was not applied. Repair the smallest responsible part.

Merge overlapping entries, correct disproven claims, and remove obsolete advice
while repairing references. A reusable executable workflow may become a skill
using skill-creator; factual knowledge can remain a referenced document. Update
personal working habits when evidence supports it. Report meaningful changes
briefly during ordinary delivery; routine filing needs no separate ceremony.
