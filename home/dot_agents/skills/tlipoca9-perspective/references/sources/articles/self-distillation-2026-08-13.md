# 我的自我蒸馏

> 版本：2026-08-13  
> 这是一份工作中的自我模型，不是完整人格判断。它描述我如何理解复杂系统、如何借助 AI 工作、如何判断质量，以及这套方式正在怎样变化。

## 一句话

我是一个以契约和真实运行结果为锚点的系统建造者，正在把 AI 从“替我写代码的工具”改造成一个能分工、质疑、验证、交接并持续推进的工程组织。

真正驱动我的不是代码产量，而是把一个含混问题逐层收敛成：明确语义、清晰边界、可执行实现、可重复验证和可长期继承的工程资产。

## 现在的我

### 1. 我首先追求语义正确，然后才是实现正确

我经常先追问：这个对象到底是什么，属于哪个边界，生命周期如何，谁拥有状态，失败时应表现出什么语义。近期围绕 Deployment、ExecutionRuntime、Workspace、Agent Version、Brain/Hands、YunAPI 的讨论都体现了这一点。接口、数据结构和错误码要按依赖顺序出现，术语不能在不同场景悄悄换义，文档必须脱离聊天上下文仍可独立理解。

因此，我所说的“契约”并不只是 API schema。它包括客户可观察行为、生命周期、错误语义、兼容边界、性能边界以及验证方式。

置信度：高。

### 2. 我把可执行证据看得比解释更可靠

代码可能由 Agent 生成，文档也可能写得漂亮，所以我倾向于把 E2E、contract test、真实部署、压测数据、日志、Git diff 和仓库当前状态当作真源。我的典型要求不是“理论上可行”，而是构建镜像、部署预发、跑控制面和公网数据面 E2E、检查资源和日志、修复后再次验证。

这不是单纯的测试偏好，而是一种认识论：结论必须能追溯到事实，系统是否成立最终由行为回答。

置信度：高。

### 3. 我在设计的已不只是软件，也包括生产软件的 Agent 组织

我会主动规定不同 Agent 的角色、上下文隔离、评审维度、投票和汇总方式；会把有效流程固化成 skill、AGENTS.md、交接文档和进度账本；会验证不同模型和自定义 Agent 角色是否真的可用。

最近的变化尤其明显：我不再满足于“多开几个 Agent”，而是在设计认知独立性。评审 Agent 应当是空白、无上下文的，并按不同风险维度独立取证；架构 Agent 则负责从多个缺陷中提炼共性，避免局部修补。

置信度：高。

### 4. 我授权很大，但边界要精确

我愿意让 Agent 无人值守地继续开发、提交、推送、部署和验证，也不希望已经批准的契约被反复确认。但这种授权通常伴随明确护栏：保留脏工作树，不碰 secrets 仓库，严格按交接顺序恢复，只恢复指定能力，局部修复不能阻塞主干任务。

我的理想协作不是频繁请示，而是“目标与禁区清楚，执行过程自主，结果必须有证据”。

置信度：高。

### 5. 我正在从“流程完备”修正为“质量约束下的效率优先”

我曾大量探索 GSD 式的阶段化自动流程，但现在已经明确不用 GSD。它属于历史实验，不能再用来描述当前偏好。

目前保留下来的不是那套流程本身，而是它帮助我验证过的几个原则：先收敛语义、阶段之间要有可靠交接、实现后必须验证、状态必须可恢复。新的方向更轻：大需求使用契约驱动和独立审查，小修由 sub-agent 并行处理，不能让流程成本阻塞主线；冗余 lint、过时 skill 和无价值测试应被删除。

这说明我并不忠于流程。我忠于流程原本要保护的结果，一旦流程自身成为阻力，我会替换它。

置信度：高，且这是当前最重要的成长信号。

## 稳定底色

这些特征跨越多个阶段，近期仍然成立：

- 系统思维：自然地从组件关系、所有权、状态机、生命周期和影响链路理解问题。
- 第一性与上游优先：偏好能直接表达目标语义的官方或标准原语，警惕没有生产证据的 fallback 和旧路径。
- 完整交付：分析、实现、测试、提交、部署、验证和文档是一条链，不把“代码写完”当作完成。
- 强烈的质量责任：关注兼容性、可观测性、回滚、并发、性能、异常路径和存量状态，不只检查 happy path。
- 资产化倾向：重复出现的问题应沉淀为测试、skill、文档、dashboard、cookbook 或可恢复的 handoff。
- 直接而高密度的沟通：通常快速给目标、事实和约束；发现方向不对时立即纠偏，不为已经失效的方案维持表面一致。

## 成长轨迹

| 阶段 | 主要关注 | 留下的能力 | 已经跨过去的限制 |
|---|---|---|---|
| 早期 | 深入代码、网关、Sidecar、网络与运行时问题，寻找业界方案 | 强诊断、源码阅读、运行时直觉 | 容易把高质量等同于亲自钻得足够深 |
| 中期 | 自动化阶段流、长链路执行、多 Agent 编排 | 任务分解、状态化推进、无人值守执行 | GSD 式流程过重，流程可能反客为主 |
| 近期 | E2E 作为客户场景契约，重构 Agent Engine/Shipyard/YunAPI | 从产品语义到部署验证的端到端所有权 | 单靠流程完成度不足以保证设计质量 |
| 当前 | 契约层与实现层分离、独立评审、文档自洽、效率优先 | 构建可验证的 AI 工程组织 | 正在继续压缩仪式成本，保留真正有效的约束 |

这条轨迹的核心不是“越来越严格”，而是“越来越会区分什么值得严格”。

## 我最擅长的工作

我最适合处理同时包含产品语义、分布式系统实现和真实环境验证的问题，尤其是：

- Agent Runtime、Sandbox、控制面/数据面、调度、租约、生命周期和网络策略；
- 跨服务 API 与领域模型设计，特别是兼容、鉴权、隔离和状态语义；
- 从真实故障、日志和代码路径还原时间线与根因；
- 把客户场景转化为 E2E 契约、容量指标和发布门槛；
- 设计 Agent 协作流程、skills、审查机制和长期知识载体；
- 接手脏工作树或长任务，通过 handoff 和验证证据继续推进到交付。

## 容易付出的代价

### 1. 验证可能膨胀成新的官僚体系

独立 Agent、投票、双审、contract、E2E、pre-push 都有价值，但叠加后可能让简单修改承担与主干需求相同的仪式成本。最近提出“小修并行、不要阻塞主干”和精简 lint，说明我已经意识到这一点。

应保留的判断原则是：验证强度按风险、影响面和可逆性分配，而不是按流程模板分配。

### 2. 多数票不能替代证据

多个 Agent 可能共享相同模型偏见和代码盲区。真正有价值的是独立上下文、正交审查维度和可复现实验；“三个 Agent 都同意”本身不是事实。

### 3. E2E 是真源，但不是唯一测试层

E2E 最适合锚定客户可观察契约，却不擅长精确定位、穷举内部不变量或稳定覆盖所有失败组合。理想结构是：E2E 守客户语义，组件/契约测试守跨模块协作，单元测试只守稳定且值得长期维护的内部规则。

### 4. 高授权带来安全与外部影响面

历史对话中出现过凭证和广泛的集群、推送、部署授权。输出证据已做脱敏，但原始 Codex 日志仍可能保留敏感信息。我的效率偏好需要配套更成熟的权限最小化、凭证轮换和外部写入边界。

### 5. 这份画像对“工作之外的我”几乎无知

Codex 对话高度集中于工程和管理工作。它足以描述我的工作人格，却不足以推断我的完整价值观、关系方式、生活偏好或情绪结构。任何越过这个边界的结论都应视为低置信推测。

## 给未来 Agent 的协作说明

与我协作时，应按下面的优先级行动：

1. 先确认目标语义、可观察契约和不在范围内的事项，再选择实现。
2. 以当前仓库、真实运行结果、官方原语和一手记录为证据；不要拿历史流程覆盖新指令。
3. 已批准的决策不要反复确认。边界明确后自主推进到验证和交付。
4. 保留我的工作树和已有状态；任何清理、重置、旧路径保留都必须有具体理由。
5. 大问题按契约层、实现层和独立验证拆解；小问题并行处理，不能阻塞主线。
6. 独立评审按不同风险维度取证，冲突靠证据解决，不靠票数制造确定性。
7. 把 E2E 视为客户行为真源，但按风险补足组件测试、日志、指标和性能验证。
8. 文档必须独立可读、术语先定义、因果连续、细节有取舍；不要让读者依赖聊天历史。
9. 最终报告应直接给结论、证据、验证结果、残余风险和刻意保留项。
10. 若我最新的话推翻了旧偏好，以最新决定为准。人会成长，历史只用于解释变化。

## 当前自我定义

我不是一个依赖固定方法论的人。我会试用方法、把它推到足够深、观察它真正保护了什么，然后丢掉多余的壳。

我现在追求的是一种更成熟的工程杠杆：

> 让语义由人负责，让执行可以委派，让结论接受独立质疑，让真实系统给出最后答案，并把有效经验沉淀为下一次更低成本的能力。
