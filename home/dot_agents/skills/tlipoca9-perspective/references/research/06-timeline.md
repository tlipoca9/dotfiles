# 工作思维演化时间线（2026-03-16 至 2026-08-13）

> 调研维度：时间线与思想转折。  
> 信息模式：纯本地语料；未使用网络搜索。  
> 结论口径：越近的行为权重越高；用户最新明确修正可覆盖历史频次。

## 核心结论

这五个月的主线不是“从不使用流程到使用流程”，也不是“越来越严格”，而是：

> 从亲自深入运行时与网络链路寻找真因，在此基础上试验重型阶段化自动流程；随后把 E2E 提升为客户行为契约，再把契约层与实现层拆开、让无上下文 Agent 独立取证；最终开始主动删除流程冗余，形成“高风险事项严格验证、小修不阻塞主线”的效率观。

预设轨迹“深度亲自排查 → 流程自动化实验 → E2E 客户契约 → 契约驱动 / 独立审查 / 效率优先”总体成立，但只能理解为**重心迁移**，不能理解为互不重叠的四段。GSD 在最早的 2026-03-16 已经出现，深度排查与流程实验长期并存；真正清晰的断点是 2026 年 7 月：GSD 实际使用骤降，而 E2E、客户场景、产品语义和独立审查成为新的中心。

截至 2026-08-13，GSD 已由用户明确声明“不再使用”。它是**已淘汰的历史实验**，不是当前偏好。当前保留的是它曾帮助验证的原则——语义先收敛、阶段可交接、实现后验证、状态可恢复——而不是 GSD 这套流程本身。

这份蒸馏的最终用途也已由用户明确：**不是让 Agent 模仿人格或口吻，而是减少用户反复替 Agent 纠偏。** 因此，时间线的交付价值在于把历史中的反复纠偏提炼为当前防漂移协议：遇到新任务时，应优先执行最近、最明确的决定；旧做法只用于解释为何变化，不能以“历史上经常这样做”为理由覆盖新决定。

- **事实**：用户提示词、明确决定或语料统计直接支持。

- **未知**：现有 Codex 对话不足以判断，或只能看到意图而看不到最终效果。

## 阶段一：深入技术现场，以真实证据压缩不确定性

**时间：2026-03-16 至 2026-04-26**

这一阶段的技术主线集中在 `zeroproxy`、Sidecar、eBPF、CA 信任注入、NetworkPolicy、凭证托管和 WASM Hook。问题通常沿真实请求路径展开：客户端、网关、代理、Sandbox、证书库、系统调用和网络协议逐层排查。

### 已验证事实

- 3 月 17 日询问 Sidecar 模式注入 eBPF 的完整步骤，并要求说明和架构图；同日设计 qclaw 身份令牌到 credential 的映射、验证链路和多身份提供商扩展边界。
- 4 月 23 日围绕一条明确的 trace 追查 `client -> sandportal -> cube-proxy -> sandbox` 链路，并指出 Sandbox 已返回 403，要求解释为何上游未按预期返回。
- 4 月 24 日要求代码审查“只使用仓库中的具体证据”，包括提交、PR、路径、diff、失败测试与 CI；证据不足就跳过，并要求遵守 RFC 等真实协议知识。
- 4 月 25—26 日从用户程序如何信任自定义 CA，推进到对 Envoy、Istio、AgentGateway 等开源实现的源代码调研和 WASM Hook API 设计。
- 这时已经使用 GSD：3 月 16 日出现 resume / milestone / plan / execute，3 月 17 日要求“每个独立 GSD 应该是一个独立 subagent”；4 月 11 日进一步规定 discuss、plan、execute、verify 分别由 subagent 承担。

### 阶段推断

这一时期“高质量”的中心仍是**把自己放进系统内部**：读源码、看 trace、核对监听端口、复现网络行为、对照协议，然后给出最小且可验证的解释。AI 的主要价值是扩大搜索与排查带宽，但问题定义和证据标准仍由用户强力掌控。

GSD 并不是在深度排查之后才出现，而是早期就作为并行的执行外壳存在。更准确的说法是：先形成了“真实系统与代码证据优先”的认识论，随后不断把这套认识论编码进 Agent 流程。

### 当时尚未解决的限制

从 Codex 语料无法证明用户亲自完成了每一次底层排查；能确认的是，他反复指定了排查链路、证据类型和验收标准。是否因此形成了对个人深度介入的过度依赖，只能作为中等置信度推断。

## 阶段二：把个人判断写进流程，试验阶段化无人执行

**时间：2026-04-27 至 2026-06-20**

这一阶段 GSD 与自定义工作流明显增多，6 月有 92 个会话命中 GSD，是全周期峰值。流程被拆成讨论、计划、预验证、执行、独立验证、返修循环与里程碑收敛；同时，Sidecar Runtime、Supervisor、AccessPolicy、快照、暂停恢复、日志与健康检查等生产能力持续推进。

### 已验证事实

- 4 月 27—29 日反复要求每个 discuss / plan / execute / verify 阶段使用独立 subagent，verify 必须找到真实问题并推动修复，不接受“这是已有问题”作为免责理由。
- 5 月 3 日定义 Archon 工作流：先参考生产就绪开源实现，再用脚本 pretest，之后由分离的 execute 与 verify Agent 循环，直到验证 Agent 不再发现问题，同时坚持 `simple and stupid`。
- 5 月 18 日要求不同 subagent 分别审查快照制作、匹配、冷启动、预创、Sidecar 及其正交组合；这说明并行审查已经开始按风险维度拆分，而非仅按文件拆分。
- 6 月 9—18 日大量使用 GSD 研究、规划、执行与评审制品，调研和 review 均写入阶段文件，形成可恢复的流程状态。
- 6 月 20 日明确提出：“只固化实现形状、没有稳定行为价值”的测试没有价值，存量也应删除。该判断直接否定了“流程产物越多越好”。

### 技术、产品与团队视角的扩张

这一时期技术问题开始被客户生产场景重新组织。众安的日志轮转、四层数据库连通、暂停恢复、磁盘坏块、SRE 登录审计、健康检查、存量实例修复，以及智谱、美团等客户的兼容与 Hook 需求，不再只是单点 Bug，而被转译为平台能力、SLO、逃生通道、兼容边界和回归场景。

5 月 18 日的周报要求“不太相信旧周报”，要从客户上量、卡点、产品与技术需求、产品洞察及流程改进重新核对；6 月 3 日追问能否从 SLO 定义反推出工作。这是从“把问题修好”走向“由客户结果反推工程优先级”的明确信号。

### 阶段推断

GSD 的价值在这里达到峰值：它把用户原本高度依赖个人判断的工作拆成可交接、可重复、可无人值守推进的阶段。但同一时期已经出现反作用信号：要求“收敛，不要新开 reviewer”、清理中间态说明、删除只守实现形状的测试。这意味着用户开始区分**流程保护的结果**与**流程本身**，不再把产物数量等同于质量。

### 未知

现有语料可以证明流程被频繁调用、被不断修改，但不能独立证明它在吞吐、缺陷率或交付周期上优于轻量流程。GSD 的实际成本收益没有统一量化记录。

## 阶段三：E2E 从“测试集合”升级为客户行为契约

**时间：2026-06-18 至 2026-07-09（与阶段二有意重叠）**

转折从 Berth / BerthV2 和新 Agent Engine 的重构中出现。用户不再从旧实现内部逐块搬迁，而是要求先重写 E2E，重新定义系统应该对外表现什么行为。

### 已验证事实

- 6 月 18 日启动 Berth 的完全重构时明确说：“打算从 e2e 测试的重新定义开始”；新 E2E 不关心服务名，只依赖 Berth 的 gRPC 与 HTTP 端点。
- 6 月 20 日否定只固化实现形状的测试，建立“稳定行为价值”作为测试是否值得存在的标准。
- 7 月 2 日主动区分测试层次：Berth 原来称为 E2E 的测试更像集成测试，应该白盒检查 DB / Redis；顶层 E2E 则应保持黑盒并围绕外部端点。
- 7 月 3 日明确表述：“代码都是 agent 写的，我希望 e2e 作为代码契约，守住真源”，并要求 Agent 生命周期不能只测 happy path。
- 同日授权 Agent 自行加日志、本地复现、修复、推送、重新部署验证，并要求遇到的问题尽可能沉淀成新的 E2E 场景。
- 7 月 6 日把 `e2e` 仓库直接描述为“API 契约”，并在重庆预发布环境验证 Agent、AgentVersion、WorkspaceTemplate、Workspace 等资源接口。

### 阶段推断

这是认识论上的关键变化：代码可能由 Agent 大量生成，内部结构也会被频繁重构，因此实现不再适合作为唯一真源。用户把 E2E 提升为**客户可观察行为的冻结层**，让实现可以被委派和替换，只要客户契约、兼容性与真实环境行为仍成立。

AI 协作也因此从“严格按阶段做完工作”转向“在已冻结的行为边界内高度自治”。用户授权扩大，但不是无边界授权：配置来源、目标集群、镜像架构、兼容语义、脏工作树和验证路径都被明确限定。

### 产品视角

API 是否暴露 ProviderKind、ClientToken 是否可选、External Agent 怎样保持对外兼容、资源如何按租户隔离，都开始从客户可理解性和产品抽象而非内部实现便利出发。E2E 不只验证接口能调用，而是验证客户旅程能持续成立。

## 阶段四：从服务重构走向产品语义与端到端系统所有权

**时间：2026-07-10 至 2026-08-04**

技术主线进一步集中到 Agent Engine：Customs、Berth、Shipyard、Shipyard-YunAPI、Brain / Hands、Execution Runtime、Environment / Workspace、租约、隔离、可观测性和性能容量。关注点从“每个组件有没有实现”扩大为“整套产品如何被定义、使用、运行和运营”。

### 已验证事实

- 7 月 10 日要求统一重构 Workspace / Environment 相关概念，连带错误码、日志、目录、接口和数据库表，说明术语一致性已被视为系统级问题，而不是文案问题。
- 7 月 15 日按四个服务盘点 OpenTelemetry 指标，并追问数据面耗时是否按 provision 等高差异阶段拆开。
- 7 月 16—17 日调研 AWS AgentCore 的用户旅程，并连续追问“一个完整的产品视角的 Agent Engine 应如何推导”，起点是先定义 Agent，再决定产品切入面。
- 7 月 17 日把服务隔离边界从内部 Account ID 调整为对客户有意义的 Group ID / YunAPI AppID。
- 7 月 23 日提出“cookbook 描述客户使用场景，E2E 锚定客户使用场景的可用性”，并从鉴权、亲和性、隔离粒度、容量配置和云资源授权继续补全产品待办。
- 7 月 29 日用真实压测数据确认 Agent Engine 在既定版本和资源配置下稳定通过 5000 QPS，并严格表述为“容量下限不低于 5000 QPS”，不把测试上限冒充系统极限。
- 8 月 4 日要求 subagent-driven 地从设计决策、存量兼容、影响链路和可观测性多个维度分析分支。

### 阶段推断

这一阶段的“完整交付”已经包括 API 语义、SDK / CLI、部署、区域 E2E、日志指标、容量、兼容与客户文档。用户承担的角色更接近跨产品与工程边界的系统负责人，而不只是某个服务的实现者。

质量观也从“发现所有 Bug”变成“让结论边界与证据强度匹配”。5000 QPS 被称为下限而非极限，是这种克制的直接例子；它与早期“真实代码证据”一致，但证据对象已从单条调用链扩展为产品级运行结果。

## 阶段五：契约层与实现层分离，追求认知独立并压缩仪式成本

**时间：2026-08-05 至 2026-08-13**

当前阶段把前面形成的原则重新组装为更轻、更明确的 Agent 工程方法：先冻结可验证契约，再分别设计和开发契约层、实现层；审查者保持空白上下文并负责不同风险维度；长任务通过 handoff 和进度账本恢复；小修并行，不得阻塞主线。

### 已验证事实

- 8 月 5 日要求至少三个 subagent 独立判断 YunAPI v3 文档是否自洽、是否能被人独立读懂，再共同投票修改。
- 8 月 6 日进一步要求每个 review Agent 都是“空白、没有上下文”的，只依据目标分支 diff，并分别专精快照制作、使用、匹配、冷启动、预创、暂停恢复等维度。
- 同日设计开发 Skill：每次修改后由三个全新 Agent 评审、投票，另设架构设计师从缺陷中寻找共性，避免局部修补。
- 8 月 7 日把新需求流程固化为：先通过讨论冻结契约并落稿，再独立开发契约层，最后由另一轮独立开发实现层。
- 同日针对文档新增约束：单独打开即可理解、术语先定义、字段与场景不冲突、不依赖聊天上下文、各局部之间有完整因果，并控制无效细节。
- 8 月 7—10 日反复以 E2E 作为 `develop-from-contract` 的契约协议，在保持 External Agent 对外行为兼容的前提下重构 YunAPI v2；8 月 10 日又按依赖拓扑排列 Deployment 的新增数据结构、接口和错误码。
- 8 月 11—12 日通过 handoff 文件恢复无人值守开发，明确冻结脏工作树、不重置，按 contract / lint / 双审、提交、镜像、重庆预发布控制面与公网数据面 E2E 的顺序完成闭环，并持续写进度账本。
- 8 月 10 日要求精简冗余 golangci 规则；8 月 11 日认为旧 integration-test Skill 已无用，应由参考 E2E 补全的 contract-test Skill 取代。
- 8 月 12 日对 `develop-from-contract` 增加“效率优先”：小修交给独立 subagent 并行处理，不得阻塞主干需求；已批准契约不要重复确认。
- 8 月 13 日用户明确说：“我已经不用 gsd 了。”

### 当前解释

“三个 Agent 投票”是这一阶段尝试的具体机制，但更稳定、更有解释力的原则是**认知独立性**：审查者不继承实现者上下文，审查维度彼此正交，结论必须能回到 diff、测试、日志和真实部署。多数票本身不是事实；多个 Agent 若共享同一盲区，票数不会增加正确性。这一点是基于整体行为的高置信度推断，不是用户逐字表述。

效率优先也不是降低质量门槛。它把验证强度从“由模板决定”改成“由风险、影响面和可逆性决定”：主干契约继续接受独立设计、双审、真实部署和 E2E；局部修复则并行交给 subagent，避免完整仪式吞噬主线吞吐。

## 哪些是稳定底色，哪些已经改变

### 跨阶段稳定

- 真实证据高于解释：源码、日志、trace、diff、测试、集群状态、预发布与压测始终比“理论上可行”更有分量。
- 语义与边界优先：从早期 Credential / NetworkPolicy，到后来的 Agent、Workspace、Execution Runtime、Deployment，都先追问对象定义、所有权、生命周期和兼容语义。
- 完整交付：实现、测试、提交、部署、验证、文档和后续沉淀被视为一条链。
- 资产化：重复问题倾向于变成 E2E、Skill、AGENTS.md、dashboard、cookbook、handoff 或进度账本。

### 已发生变化

- **从个人深挖到组织化取证**：仍保留深入系统的能力，但不再要求所有深度都由自己承担；更多由不同 Agent 在隔离上下文中搜集证据。
- **从流程完整到契约有效**：过程制品不再天然有价值，能保护稳定行为、兼容性和真实运行结果的约束才保留。
- **从实现视角到客户行为视角**：E2E 从测试代码升级为 API 与客户旅程的契约；内部实现可以重写，对外语义必须可验证地稳定。
- **从全面加码到按风险定价**：复杂需求保持严格契约和独立审查，小修并行处理；冗余 lint、过时 Skill 和无行为价值测试应删除。

## 已淘汰模式：GSD

**状态：已淘汰，不能写入当前身份或当前使用说明。**

历史上，GSD 帮助用户试验过阶段分解、研究落盘、执行—验证循环、可恢复状态和无人值守推进。6 月的高频使用说明这不是浅尝辄止，而是一轮充分实验。

但后续证据更强：7 月只出现“绕过 gsd”和一条旧通知；8 月 13 日用户又明确声明已经不用。根据“最新明确决定优先”的时间模型，当前 Skill 只能保留 GSD 所验证出的原则，不能建议调用 GSD，也不能用“GSD 用户”概括用户。

## 面向 Agent 的防漂移协议

这是本时间线应被下游 Skill 使用的行为约束，而不是人物模仿指南：

1. **最新决定优先。** 用户的明确修正高于历史频次；被推翻的做法进入“已淘汰”状态，不得继续作为默认建议。
2. **先守可观察契约。** 开始实现前先明确客户行为、兼容边界、失败语义和验证方式；不要用内部实现细节替代契约。
3. **以当前证据纠偏。** 先读当前仓库、diff、测试、日志和真实环境，再使用历史经验；历史不能覆盖已变化的代码与需求。
4. **把审查设计成独立取证。** 对复杂或高风险变更，按正交风险维度使用空白上下文审查者；冲突靠可复现实验和证据解决，不靠票数制造确定性。
5. **授权范围内持续推进。** 目标、禁区和契约已明确时，不反复请示；保护脏工作树和既有状态，通过 handoff、进度账本、提交、部署和验证完成闭环。
6. **按风险支付流程成本。** 主干需求使用契约层 / 实现层分离和独立验证；小修交给 subagent 并行处理，不得阻塞主线。
7. **删除失效外壳。** 无稳定行为价值的测试、冗余 lint、过时 Skill 和中间态说明不因“曾经有用”而保留；GSD 同样属于这一规则。
8. **不模拟用户本人。** 输出应体现用户的判断约束和证据偏好，但不要假装拥有用户未表达的经历、情绪、关系或价值观。

## 仍然未知

- 这些流程变化对交付周期、线上缺陷率和团队吞吐的净影响，没有统一、可比较的量化数据。
- Codex 对话能观察到用户对团队协作、周报、分工和客户承诺的要求，但不足以还原正式组织角色、汇报线和最终决策权。
- “三个 Agent 投票”是否会长期保留未知；从 8 月 12 日的效率修正看，更可能长期保留的是独立上下文、正交维度和证据复现，而不是固定 Agent 数量。
- 对工作之外的人格、生活选择和价值排序没有足够语料，本时间线不作推断。
