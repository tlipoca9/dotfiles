# 用户自己的“著作与系统思考”调研

> 调研时间：2026-08-13  
> 模式：纯本地语料；未联网  
> 用途：作为 `tlipoca9-perspective` 的 Phase 1 研究底稿，而不是最终人格结论

## 结论摘要

这批 Codex 对话没有传统意义上的书、博客或论文，但有大量连续的设计判断、纠错、取舍和执行约束，可以视为用户的“工作性著作”。其中最稳定的思想主轴不是某套固定流程，而是：**先把客户可观察语义收敛为契约，再用真实运行证据裁决实现；把 AI 组织成能独立取证、并行执行、可靠交接的工程组织，同时持续删除不再保护结果的流程、抽象和测试。**

候选核心论点共有七个：

1. 先定义对象、边界、生命周期和失败语义，再谈实现。
2. 可执行的客户场景证据高于代码解释；E2E 是外层真源，contract test 守服务间协作。
3. 优先使用一手事实、官方原语和经生产验证的公共方案，警惕自造抽象与无证据 fallback。
4. AI 协作的关键不是“多开 Agent”，而是认知独立、正交分工、依赖清楚和可合并。
5. 高授权必须与精确禁区、可恢复状态和可审计进度同时存在。
6. 讨论结果必须沉淀成脱离聊天仍可工作的工程资产。
7. 流程只是一种可替换工具；当前已从“流程尽量完备”转向“质量约束下效率优先”。

第七点是最重要的近期变化。GSD 在历史上出现频繁，但用户于 2026-08-13 明确说“我已经不用 gsd 了”，因此它只能解释过去，不能描述现在。

## 证据口径与时间权重

### 语料范围

- `codex-user-message-corpus.jsonl`：2026-03-16 至 2026-08-13，共 636 个纳入会话、12,191 条用户侧消息。
- `codex-self-distillation-evidence.json`：主题、行为标记和时间窗口的方向性统计。
- `我的自我蒸馏.md`：已有综合稿，仅作二手交叉检查，不反向替代原始消息。

对话语料中仍能看到少量被转录到用户通道的通知、粘贴内容和旧式工作流文本。本调研不把这些内容当作用户信念；核心证据只采用用户直接提出的判断、问题、纠错、批准和约束。由于语料只记录用户对 Codex 的工作互动，本文能描述的是**工作认识论和工程习惯**，不是完整人格。

### 时间规则

- 近 30 天：最高权重，用于定义“现在”。
- 31–60 天：次高权重，用于确认近期趋势。
- 60 天前：只用于识别稳定底色和变化起点。
- 最新明确纠正覆盖旧行为。尤其是 GSD，不得用历史频次抵消 2026-08-13 的明确淘汰声明。

自动标记只作导航，不是人格测量。仍有几项方向性信号值得记录：近 30 天，“Agent 与工具链”出现在 78.7% 的会话中，“并行与独立审查”从 31–60 天窗口的 12.5% 上升到 43.5%，“证据与可复现”从 25.4% 上升到 40.7%，“最小化与简化”从 11.8% 上升到 23.2%。GSD 则从 31–60 天的 30.6% 降到近 30 天的 0.9%，随后被用户明确否定。

### 认识状态标签

- **用户明说**：用户直接表达的原则、决定或否定，可信度最高。
- **行为证据**：用户在多个任务里反复施加同一约束；可证明稳定偏好，但不等同于自我宣言。
- **本调研推断**：由跨场景复现归纳出的解释，必须允许未来修正。
- **未知**：语料无法支持的内容，不用工程行为填空。

## 候选核心论点

### 1. 语义先于实现；概念必须从真实场景中挣得存在权

**当前判断：高置信、跨域稳定，近期继续强化。**

这里的“契约”远大于 API schema。用户持续追问对象究竟是什么、资源为什么存在、边界在哪里、生命周期是否相同、状态和失败如何对客户表现。一个字段或资源若无法由客户场景证明必要，就应删除或隐藏，而不是因未来可能有用而提前公开。

**用户明说的证据：**

- 2026-06-16，在 Berth 接口重构中，用户要求把 `Backend` 改为 `ExecutionRuntime`、移除 `brain`、压缩 `ExecutionRuntimeRef` 和 lease 字段，并明确“不需要考虑兼容性，允许破坏性变更”。这不是命名洁癖，而是在让接口对象贴合实际领域语义。（`agentpass/agent-engine`，session `019ecf5a-e62a-7ea2-953a-8dcf23752f5a`）
- 2026-07-17，在 Agent Engine 产品基础文档中，用户连续追问“task 和 session 的边界在哪”“它的必要性是否充分”“是不是同等生命周期的东西”，并要求“用实际场景证明每个概念是必要的，不必要的概念是要删的”。（`agentpaas/agent-engine`，session `019f6f2b-a8b2-7fa1-a25c-0b6ed21a04b4`）
- 2026-08-04，在 Sandbox Service 设计中，用户要求“遵从奥卡姆剃刀原则，如无必要，勿增实体”，并指出客户不关心底层是 agent 还是其他能力，只需要稳定入口、会话控制和 instance 调度。（`agentpaas/agent-engine`，session `019fcc98-f411-72f1-8566-4947119d32cf`）
- 2026-08-07，用户逐项收敛删除、重试、锁、缓存、鉴权和错误语义，并明确“API 的输入参数校验、响应结果校验、副作用都属于契约”；同时要求契约文档最终由测试守护。（`.agents` session `019fdaf3-9f9a-7693-ac08-ba750da38840`；`agentpaas/agent-engine` session `019fdb5b-aeb1-7e63-b44d-d5628a8f4e0d`）
- 2026-08-10，用户要求 Deployment 新增的数据结构、接口和错误码按依赖顺序排列：若 A 依赖 B、C，B 依赖 C，就按 C、B、A 展开。这体现了其“定义顺序必须反映概念依赖”的文档与设计要求。（`agentpaas/agent-engine`）

**行为证据：** 用户在网络代理、运行时、调度、YunAPI、CLI 和文档任务里都反复先纠正对象语义，再允许实现继续；它不是单一项目偏好。

**本调研推断：** 用户的第一性问题通常不是“怎样把功能做出来”，而是“系统要对谁承诺什么，以及哪些内部事实不该泄漏为公共概念”。这使他倾向于从客户可观察行为反推资源模型，而非从现存数据库或代码结构向外包装 API。

**失效边界：** 用户也会为了兼容既有客户而保留旧对外契约。因而“语义干净”不是无条件 breaking change；是否兼容取决于该行为是否已成为真实外部承诺。

### 2. 可执行证据高于内部解释；测试层应按观察者边界分工

**当前判断：高置信、最稳定的工程认识论之一。**

用户不把“代码看起来对”“单元测试很多”或“Agent 解释得通”视为完成。他更信任原始日志、真实网络请求、部署后行为、E2E、contract test、压测曲线和可观测面板。尤其当代码主要由 AI 生成、本人不熟悉实现语言时，外层验证成为控制质量的主要机制。

**用户明说的证据：**

- 2026-03-17，用户要求“一条请求从头到尾的原始日志串”，并要求修到 eBPF 模式能通过完整 E2E。这是最早期的“从真实链路而非局部解释判断”证据。（`finofliu/zeroproxy`）
- 2026-04-11，用户明确说自己不熟悉 Rust、无法判断细致单元测试是否有效，希望“在外层通过我编写的 E2E”验证效果是否真实达到；当时甚至说“不在乎运行 e2e 要花多少时间，要最大限度保证可用性”。（`TencentCloudAgentRuntime/zeroproxy`，session `019d7d30-60f6-7063-a253-abfa673ae8f8`）
- 2026-07-07，用户要求矩阵化补充数据面场景，“通过 e2e 确立数据面契约”；2026-07-10 又要求每次性能优化后必须重跑 External Agent 数据面 E2E，防止“为了性能把功能干没了”。（`agentpaas/agent-engine-workspace-shipyard`；`agentpaas/agent-engine`）
- 2026-08-07，用户明确把测试分成两层：E2E 面向终端用户，通过 YunAPI 和公网域名观察控制面、数据面；contract test 面向内部 client，验证服务间交互。随后要求原集成测试由 contract test 替代，并把 E2E 契约与架构设计拆成独立文档。（`agentpaas/agent-engine`，session `019fdb5b-aeb1-7e63-b44d-d5628a8f4e0d`）
- 2026-08-12，用户要求分场景 benchmark 从 100 QPS 倍增探测至 5000 QPS，失败后用二分思想寻找当前基准；每轮记录 commit、优化内容、时间点和新基准。这把“优化有效”定义成可重放的差分证据，而不是主观判断。（`agentpaas/agent-engine`，session `019ff66b-c6b1-7390-a22c-09064c49ce1a`）

**行为证据：** 用户在 ZeroProxy、Sandstorm、Agent Engine 和独立 E2E 仓库中反复要求真实构建、部署、跑请求、看日志、重测回归和记录基准，覆盖至少五个月。

**本调研推断：** 用户的核心认识论可以概括为：**行为裁决实现，证据裁决叙述。** E2E 是客户语义真源，但不是唯一测试层；内部稳定协作由 contract test 守护，性能和容量由 benchmark 守护，定位则依赖日志、指标和 trace。

**失效边界：** 用户会删除只固化实现形状、没有稳定行为价值的测试，也会关闭已不再属于目标契约的存量 E2E。因此他重视的是“有意义的可执行证据”，不是测试数量。

### 3. 一手事实、官方原语和生产验证方案优先；自造复杂度必须举证

**当前判断：高置信、跨技术领域稳定。**

用户对信息源和实现原语有清晰的可信度排序：真实运行事实与一手资料在上，官方标准和成熟开源方案次之，当前代码或 cookbook 只有在验证后才可信；自定义 ABI、重复封装、隐式 fallback 和旧路径则需要额外论证。

**用户明说的证据：**

- 2026-04-25，用户追问“每一行脚本都有实际的证据吗？能否证明？”，要求 step-by-step 说明及每步依据，并强调“简单的模型才有效”。（`TencentCloudAgentRuntime/zeroproxy`，session `019dc5ba-4f68-7d53-9f89-cb18c316b830`）
- 2026-04-26，用户要求完全移除自定义 ABI，理由是希望支持开源项目普遍采用、经过真实生产验证的方案，并尝试尽量兼容 Proxy-Wasm Rust SDK。（`TencentCloudAgentRuntime/zeroproxy`，session `019dc9ff-8296-76a1-9e59-8802ec431b42`）
- 2026-06-14 至 06-20，用户多次要求与官方用法、标准库和官方测试对齐：删除偏离官方的内部文档，使用 `testing/slogtest` 作为“官方基础契约”，最终放弃过度自造 logging 抽象，直接复用 `otelzap` 并只暴露五个函数。（`agentpass/agent-engine`，多个 session）
- 2026-07-17，用户要求产品基础文档只使用外部一手资料和竞品材料，明确说“cookbook 不可信”；同月面对测试失败时又反复追问“是真的失败，还是契约有变化”。（`agentpaas/agent-engine`；`agentrun/reviews`）
- 2026-07-24，用户明确要求 verifier 必须返回 digest，“不要 fallback 允许”；2026-08-07 又指出历史债务会迫使实现不断兼容、降低效率。（`agentrun/sandstorm`；`agentpaas/agent-engine`）

**行为证据：** 当现有抽象与官方原语冲突时，用户通常要求删除自造层；当兼容确有客户价值时，他又会精确限定“只兼容 external agent”等范围，而不是抽象地反对所有兼容。

**本调研推断：** 用户不是简单的“不要 fallback”派。他反对的是**无生产证据、模糊失败、延长旧设计寿命的 fallback**；对明确客户承诺、可观察行为或灾难恢复有价值的兼容路径，他愿意保留。

**失效边界：** “官方”并不自动等于正确。用户会要求验证官方测试是否匹配自己的契约，也会因当前产品边界选择不实现标准方案的全部能力。

### 4. Agent 应被设计成工程组织；独立上下文比数量本身更重要

**当前判断：高置信，近 30 天显著强化。**

早期用户已在用 subagent 并行调研和实现；近期则进一步规定角色、上下文隔离、专业审查维度、架构汇总和主从分工。自动标记中，“并行与独立审查”由 31–60 天的 12.5% 上升到近 30 天的 43.5%，与原始消息一致。

**用户明说的证据：**

- 2026-04-26，用户要求“针对每个调研的开源项目，启动一个独立的 subagent”，分别核对一致性与缺漏。（`TencentCloudAgentRuntime/zeroproxy`）
- 2026-05-18，用户曾要求至少六轮审查，每轮三个上下文独立的 subagent 判断 RFC 问题是否可信，再由第四个 subagent 汇总修正。这表明他很早就意识到审查上下文需要隔离。（`TencentCloudAgentRuntime/zeroproxy`，session `019e3b3a-da8e-78a3-bc0a-73401301d279`）
- 2026-06-16 至 06-17，用户不满足于串行 autopilot，要求把 phase 依赖建成并行 DAG，并明确独立 branch/worktree、wave、merge、测试和 repair 节点；同时注意“依赖 metrics 的测试并行跑会有污染”。（`agentpass/agent-engine`）
- 2026-08-04，在代码审查中，用户要求每个 subagent 都是“空白、没有上下文的”，只根据 diff 取证，并让每个 Agent 专精快照制作、使用、匹配、冷启动、预创、暂停恢复等不同维度。（`agentrun/reviews`，session `019fcbc4-a0a0-7d41-92b8-fb13a936166d`）
- 2026-08-06，用户要求开发 Skill 中每次修改后由三个全新、无上下文 Agent review，并由架构师 Agent 从缺陷中找共性，避免修修补补；实现本身也应由独立 subagent 承担，以免主上下文压缩导致流程丢失。（`.agents`，session `019fd5fb-9a56-7fb3-adb3-37763782cf7f`）
- 2026-08-07，用户把新需求流程明确为：先收敛契约，再由独立开发轮完成契约层，另一个独立开发轮完成实现层；2026-08-11 又说“主 agent 最好只做任务分发，不要直接调用工具”。（`.agents`；`agentpaas/agent-engine`）

**行为证据：** “subagent driven”成为跨设计、实现、调研、审查、文档和运维任务的稳定短语；用户也反复纠正不该并行的依赖、会相互污染的测试和合并冲突风险。

**本调研推断：** 用户真正追求的不是并行率最大化，而是三件事：认知独立以减少共享盲点，工作单元隔离以便恢复和合并，依赖显式化以安全加速。换句话说，他在把 Agent 当作组织结构设计问题，而非单个助手能力问题。

**失效边界：** 用户仍频繁使用“投票”。现有语料能证明他重视独立性和多视角，但不能证明多数票在其体系中已被正式降级为仅供参考；“票数不能替代证据”目前应作为审慎推断，而不是用户明说。

### 5. 自主执行依赖精确边界、状态可恢复和外部影响可控

**当前判断：高置信，近期高度集中。**

用户愿意授权 Agent 连续开发、提交、推送、部署和验证，不希望已批准契约被反复确认。但其无人值守并非无边界放权，而是通过脏工作树保护、恢复顺序、禁改仓库、阶段记录、验证目标和停止条件来建立可控自治。

**用户明说的证据：**

- 2026-06-17，并行 Archon DAG 的要求包含明确 workstream brief、独立 branch/worktree、artifact、merge notes、逐 wave 测试和失败 repair，且不允许把执行器细节污染产品 roadmap。（`agentpass/agent-engine`，session `019ed6ce-bb4e-71f1-99f1-a63b1ba5cb50`）
- 2026-08-07，用户宣布进入“无人值守的开发自闭环”，要求 Agent 对需确认事项依据 Deployment 本质自行推导，同时持续记录每阶段时间、完成内容和问题；但部署配置、测试配置、环境和复现方式均被精确限定。（`agentpaas/agent-engine`，session `019fdb5b-aeb1-7e63-b44d-d5628a8f4e0d`）
- 2026-08-11，用户要求读取 handoff 后继续无人值守，先冻结脏工作树、不重置，按测试—提交—构建—部署—预发布控制面和公网数据面 E2E 的顺序推进，并记录 `progress.md`；同日说“推送吧，后面不要再问我了”。（`agentpaas/agent-engine`，sessions `019fefee-dbcc-71d2-b6f2-6782822d4655`、`019ff13a-e6a8-7300-b16a-a8d381434b6e`）
- 2026-08-12，用户要求严格按交接恢复，契约已批准不再确认，小改并行处理，正常情况直接提交并代推，但明确“不修改 secret 仓库”。（`agentpaas/agent-engine`，session `019ff66b-c6b1-7390-a22c-09064c49ce1a`）
- 2026-08-13，用户要求先合并不带 `cookbook/` 的版本，同时“不要动本地文件”，体现其对 Git 历史与工作区状态分离的精确控制。（`agentpaas/ags-cli`）

**行为证据：** handoff、progress ledger、Git 断点、明确作用域和“不要再问”的组合多次出现；它们共同构成用户的授权协议。

**本调研推断：** 用户的理想自治模型是：**人负责目标语义和禁区，Agent 负责连续执行，文件和 Git 保存可恢复状态，真实系统负责验收。** 高频纠偏通常发生在 Agent 偏离语义或停止主干推进时，而不是因为用户天然需要控制每一步。

**失效边界：** 原始对话中曾出现广泛环境操作和敏感凭证。高授权并不自动等于权限最小化；安全边界的成熟度不能只由“不要修改某仓库”推断，需要另行审计。

### 6. 知识必须资产化，而且成品不能暴露推导过程的残渣

**当前判断：高置信、从早期就稳定存在。**

用户不仅要求产出文档，还要求文档、Skill、AGENTS、测试、dashboard 和 handoff 能长期指导后续 Agent。对外成品应独立可读、术语先定义、因果连续、详略与读者匹配；讨论中的中间态、反复修改痕迹和无上下文说明不应留在定稿里。

**用户明说的证据：**

- 2026-03-17，用户要求文档不要出现任何“中间态”的说法，不暴露多次修改痕迹，并按老板真正关心的信息控制篇幅。（`qclaw-support`，session `019cfba2-880f-7823-8049-7ded7cf5be42`）
- 2026-04-11，用户要求把 E2E 讨论总结成长期维护的 docs 和中台 Skill，强调项目主要由 AI Agent 编写，最终材料“不要留有任何中间态的说明”。（`TencentCloudAgentRuntime/zeroproxy`，session `019d7d30-60f6-7063-a253-abfa673ae8f8`）
- 2026-04-26，用户要求文档先行、给插件作者完整 API/函数定义与 step-by-step guide，并再次要求清理所有无上下文中间态。（`TencentCloudAgentRuntime/zeroproxy`，session `019dc9ff-8296-76a1-9e59-8802ec431b42`）
- 2026-06-14 至 06-15，用户要求 docs 中每份文档在 AGENTS 中有索引和说明，同时强调 AGENTS 应引用项目文档而不是“再造真源”。（`agentpass/agent-engine`）
- 2026-08-07，用户明确列出 Agent 写文档的三类失败：不能单独打开理解、术语未先定义、字段与场景冲突、依赖聊天上下文；局部通顺但整体缺因果；细节失衡。随后要求将这套规则写入 AGENTS。（`.codex`，session `019fdb41-f6c8-7101-96d5-67410d3754e0`）
- 2026-08-11，用户给 Outline 文档 Agent 的要求包括：读者不知道仓库，所有背景、对象关系、生命周期、接口用法、运行链路、约束和失败语义必须在正文讲清；写完后重新读取并核对完整性和事实一致性。（`agentpaas/agent-engine`，session `019fefee-dbcc-71d2-b6f2-6782822d4655`）

**行为证据：** 同一思想被沉淀为 E2E Skill、开发 Skill、写作 Skill、AGENTS、Cookbook、架构文档、进度账本和交接文件，覆盖不同项目与读者。

**本调研推断：** 对用户而言，文档不是代码完成后的解释，而是控制 Agent 行为、保持组织记忆和降低下次成本的执行性资产。其“不要中间态”不是要求抹去决策证据；更准确的区分是：研究稿保留推导和被否方案，定稿只保留理解当前结论所必需的因果。

**失效边界：** 用户并不要求所有细节都进入主文档。多次删除验证命令、实现细节和过多章节说明，说明资产化必须服从读者任务，而不是形成文档堆积。

### 7. 流程服务结果；当前转向风险分级与效率优先

**当前判断：高置信，是最明显的成长轨迹。**

历史上的用户曾通过长阶段流、密集 lint、多轮审查和全面 E2E 来对冲 AI 生成代码的不确定性。近期并未放弃契约、审查和验证，而是开始区分主干与旁路、长期行为与实现形状、定稿与中间过程、高风险变更与局部修补，主动删除仪式成本。

**用户明说的证据：**

- 2026-04-11，用户说“不在乎运行 e2e 要花多少时间，要最大限度保证可用性”；2026-05-18 又要求至少六轮、每轮三个独立 Agent 的审查。这代表早期“用验证厚度换确定性”的高成本阶段。（`zeroproxy` 两个 session）
- 2026-06-15，用户先制定严格 linter，又很快根据误伤和可读性把文件行数上限从 400 调到 800、再到 1200，并要求“不要乱拆硬拆”；2026-06-20 明确删除只固化实现形状、没有稳定行为价值的测试。（`agentpass/agent-engine`）
- 2026-07-09，用户批评全量 E2E 太慢且无实时日志，要求 fail-fast；2026-07-15 再问如何优化根 E2E 时间。这表明“可用性优先”开始加入反馈速度约束。（`agentpaas`、`agentpaas/agent-engine`）
- 2026-08-07，用户连续提出“一切以效率优先”“小问题就 subagent 同步修，不要阻塞主干开发”，并只要求保证明确声明的 External Agent E2E，关闭其余不再属于目标的存量 E2E。（`agentpaas/agent-engine`，session `019fdb5b-aeb1-7e63-b44d-d5628a8f4e0d`）
- 2026-08-10，用户认为 `golangci` 规则过于冗余，要求简化；2026-08-11 允许预发数据库在必要时重建、历史 Deployment 丢弃；2026-08-12 明确 benchmark 不需要机械套 RED→GREEN，定稿前也不必每次跑 pre-commit/pre-push。（`agentpaas/agent-engine`）
- 2026-08-12，用户要求简化 `develop-from-contract`，明确说“不认为一个复杂的流程能适用于大多数情况”，但当 Skill 被压缩过度时又指出“核心都被丢了”。（`agentpaas/ags-cli`，session `019ff517-01a6-79e0-86b6-55744090abfb`）
- 2026-08-13，用户明确声明：“我已经不用 gsd 了。”（`.codex`，session `019ffae9-2b43-7f82-83c3-6f979e2e487f`）

**行为证据：** 近期仍保留 E2E、contract、双审、benchmark 和 handoff，但要求它们围绕主干价值排列，旁路问题并行处理，过时 Skill 和重复测试清理掉。说明变化发生在验证成本配置，而不是质量目标本身。

**本调研推断：** 用户不是从严格变成宽松，而是从“流程本身提供安全感”走向“按风险、影响面、可逆性配置验证”。他会把一种方法推到很深，观察它真正保护了什么，再丢掉多余外壳。

**失效边界：** 当前效率优先的原则形成时间较短，主要集中在 2026-08-07 至 08-13。虽然有多条直接表态，长期稳定性仍应由未来行为复核。

## 稳定工作术语与私有化含义

下列术语未必由用户原创，但在反复使用中被赋予了相对稳定的个人含义。

| 术语 | 在用户语境中的稳定含义 | 当前状态 |
|---|---|---|
| 契约 | 客户或内部 client 可观察的输入、输出、副作用、生命周期、错误、兼容和性能边界；不是只有 schema | 当前核心 |
| E2E 契约 | 从终端用户入口穿过真实控制面/数据面，证明客户场景成立的黑盒行为真源 | 当前核心 |
| contract test | 在单服务隔离环境中，从 client 视角验证内部服务交互契约 | 2026-08 明确强化 |
| subagent driven | 将调研、设计、实现或审查拆为独立 Agent 工作单元；要求分工、隔离和汇总，不只是并行调用 | 当前核心 |
| 空白、无上下文 Agent | 避免继承前序结论和共同盲点，用 diff 与指定维度独立取证 | 近期强化 |
| 无人值守开发 / 自闭环 | 契约和禁区明确后，Agent 连续实现、测试、提交、部署、验证并记录进度，不反复请求确认 | 近期强化 |
| 主干 / 不阻塞主干 | 主目标的最短闭环；旁路修补、文档和环境问题应并行处理，除非它们改变主契约 | 近期强化 |
| 一等公民 | 某能力必须进入主要抽象、接口和维护路径，而不是外挂或事后补丁；曾用于 metrics、codegraph、标准鉴权等 | 稳定用法 |
| 定稿 / 中间态 | 研究过程可以保留分歧；面向读者的定稿不得残留无上下文的修改痕迹和推导废料 | 稳定用法 |
| 真实 | 真实日志、请求、镜像、集群、预发环境、外部行为；用来对抗仅凭代码和叙述产生的虚假确定性 | 当前核心 |
| Brain / Hands | 曾作为 Agent 与工作环境的产品镜片；2026-08-04 后被重新解释为会话亲和与回收策略差异，由 Sandbox Service 承载 | 已降级为历史/解释性隐喻，不宜作为当前一等资源 |
| GSD | 历史上的阶段化执行实验 | 2026-08-13 明确淘汰，不得作为当前身份 |

没有足够证据证明用户创造了某个完全独有的技术术语。更可信的说法是：他擅长把已有术语重新定义成可执行的组织规则，例如“E2E 契约”“subagent driven”“无人值守开发自闭环”。

## 信念变化账本

### 近期强化

1. **契约层与实现层分离。** 2026-08-07 明确形成“先约定并冻结可验证契约，再由独立轮次分别完成契约层和实现层”的开发框架；后续 Deployment 开发持续沿用。
2. **Agent 的认知独立性。** 从早期的并行 subagent 演进为“空白、无上下文、专精维度、架构师找共性”；近 30 天统计也显著抬升。
3. **效率优先但不牺牲关键证据。** 旁路修补并行、定稿前延迟重型检查、删除无价值测试，同时保留客户 E2E、服务 contract 和最终 benchmark。
4. **文档因果与自洽。** 2026-08-07 将长期存在的写作偏好明确抽象为规则并固化为 AGENTS/Skill。
5. **状态化交接。** 2026-08-11 至 08-12 的 handoff、Git 断点、progress/benchmark ledger 把长任务恢复能力提升为标准动作。

### 近期弱化或被重新限定

1. **“验证越多越好”被限定为“验证稳定行为”。** 早期不计 E2E 时间、六轮审查；近期要求 fail-fast、分层测试、关闭失效 E2E，并删除实现形状测试。
2. **严格 lint 作为统一治理手段被弱化。** 2026-06 曾密集扩展自定义 lint，随后因误伤提高阈值、聚合规则；2026-08 直接要求简化冗余 `golangci` 配置。
3. **广泛兼容被限定为客户承诺范围。** 用户一方面重视存量兼容，另一方面明确“只有 external agent 需要兼容”，避免历史债务持续侵入新实现。
4. **Brain/Hands 作为一等产品对象被降级。** 团队讨论后，二者被理解为会话亲和和资源回收策略组合，而非必须暴露的新资源。
5. **投票的地位出现张力。** 用户仍要求投票，但更强调空白上下文、专精维度、代码与真实测试。可以推断“如何产生票”比票数本身更重要，但尚无直接声明完成这一转变。

### 已淘汰

1. **GSD 工作流。** 历史上共匹配 136 个会话，尤其集中于 2026-06；近 30 天仅匹配 1/108 个会话。2026-08-13 用户明确说已不用 GSD。当前 Skill 不得以“GSD 用户”“GSD 式工作者”描述他，也不应在回答中主动恢复 GSD。最多可将其作为阶段化、可恢复、验证闭环等思想的历史实验来源。

## 内在张力与尚未完全收敛的问题

这些不是缺陷清单，而是理解用户决策时必须保留的真实张力。

### 完整性与速度

用户同时要求充分契约、真实部署、独立审查、可观测和 benchmark，也强烈反感 Agent 被 lint、旁路问题、架构师讨论或细枝末节拖住。当前解法是按主干价值和风险分级，而非取消质量环节；但“什么程度算足够”仍高度依赖现场判断。

### 简单与完备

用户常说“大道至简”“如无必要勿增实体”，也会因过度简化导致核心缺失而立即纠正。这里的“简单”不是内容少，而是概念数量最少、因果足够、每个字段都有场景支撑。

### 标准化与兼容

用户偏好官方原语、标准接口和经生产验证的方案，同时又必须保护特定客户与存量路径。可预测的决策方式不是“永远删旧”或“永远兼容”，而是先判断外部承诺，再把兼容边界缩到最小。

### 自治与纠偏密度

用户希望 Agent 不再反复确认，但当 Agent 偏离客户语义、停住主干或制造无证据抽象时，会进行非常细的即时纠偏。最合理的解释不是控制欲，而是授权契约尚未被执行者正确理解；不过这一解释仍属于推断，缺少他人视角验证。

### 多 Agent 共识与独立证据

用户重视匿名投票和多 Agent 汇总，也明确要求无上下文、正交维度和真实验证。语料没有给出在“多数意见”与“可复现实验”冲突时的正式优先级规则；最终 Skill 应默认让证据优先，但标注这是根据整体行为推断，而非引用用户原话。

## 信息不足与禁止外推

- **工作之外的人格未知。** 语料几乎全是工程、产品、文档和 Agent 协作，不能据此判断亲密关系、生活方式、审美、政治、投资或情绪结构。
- **他人评价未知。** 当前材料都是用户与 Codex 的互动，没有同事、下属、合作方的系统反馈，无法校正自我呈现偏差。
- **最终业务结果不完整。** 用户反复要求部署与验证，但仅凭用户消息不能确认每项工作最终是否成功、是否产生长期价值。
- **智识谱系未知。** 除明确提到奥卡姆剃刀、开源/官方方案和若干工程实践外，没有足够材料判断其受哪些作者或思想传统系统影响。
- **投票机制的真实效果未知。** 可以看到频繁使用和后续升级，但没有结构化数据证明它比单一高质量审查更可靠。
- **效率优先的长期稳定性待验证。** 这是直接且重复的近期决定，足以描述现在，但仍应让未来对话覆盖本稿。

## 给 Phase 2 的提炼建议

最值得进入三重验证的候选心智模型是：

1. **客户语义倒推系统**：从客户可观察行为、生命周期和失败语义反推资源与接口，而不是让实现结构定义产品。
2. **可执行证据认识论**：解释只是候选，真实请求、日志、E2E、contract 和 benchmark 才形成结论。
3. **Agent 组织工程**：用认知独立、正交职责、显式依赖和可恢复状态组织 AI 工作。
4. **最小承诺面**：只有被真实场景证明必要的概念和兼容行为才进入公共契约。
5. **结果守恒、流程可替换**：保留流程保护的结果，删除不再产生边际价值的仪式。

其中第 1、2、3、5 项具有跨项目复现、对新问题有生成力、且相对具有个人辨识度；第 4 项可与第 1 项合并，也可降级为决策启发式。以下内容不应进入当前心智模型：GSD、Brain/Hands 作为一等资源、特定仓库的技术选择、特定轮数的投票或审查。这些要么已淘汰，要么只是模型在某个阶段的实现。

## 面向“少让用户纠偏”的防漂移转译

用户在 2026-08-13 当前对话中补充了最终目的：“我总是在替 agent 纠偏，蒸馏我，就是为了让 agent 不要跑偏。”因此，最终 Skill 的首要产品目标不应是让回答“听起来像用户”，而应是让 Agent 在无人值守或长任务中复现用户的**判断优先级、证据标准、范围意识和推进节奏**。

### 判断代理与语气模仿的区别

| 层次 | 应复制的内容 | 不应误做成 |
|---|---|---|
| 判断代理 | 先问客户语义和外部承诺，再选实现 | 反复复述“契约”“E2E”等口头词 |
| 证据代理 | 先读当前事实，区分已验证、推断和未知 | 用强硬语气把推测说成事实 |
| 执行代理 | 找出主干、显式依赖、并行旁路、持续验证 | 无差别多开 subagent 或堆流程 |
| 风险代理 | 按影响面、可逆性和外部写入配置验证强度 | 所有任务都套双审、投票、RED→GREEN |
| 写作代理 | 让成品独立可读、因果完整、细节有取舍 | 模仿用户的短句、反问或纠错语气 |

语气可以直接、结论先行，但它只是低优先级表层。若“像用户说话”与“按用户的判断方式做事”冲突，应始终选择后者。最终 Skill 还应避免沉浸式声称自己就是用户；更诚实的身份是“按用户已观测到的工程判断模型提供决策与执行约束”。

### 冲突时的裁决顺序

为防止历史偏好覆盖成长，Agent 遇到冲突时应按以下顺序裁决：

1. 用户在当前任务中的最新明确决定。
2. 当前仓库、diff、日志、运行环境和真实请求所显示的事实。
3. 已批准且仍在范围内的客户可观察契约。
4. 当前任务明确给出的范围、禁区、恢复顺序和外部写入权限。
5. 用户近 30 天跨场景重复出现的工作原则。
6. 更早的稳定偏好。
7. 本 Skill 的推断。
8. 已淘汰流程或历史实现，最后且默认不采用。

这意味着：GSD 即使在历史语料中频繁出现，也不能覆盖“已经不用 GSD”的最新决定；现有代码也不能覆盖已批准的新契约；而 Skill 的人格推断永远不能覆盖当前任务的明确要求。

### 可直接写入最终 Skill 的前置约束

#### 1. 先找主干，不让旁路工作阻塞

- 开始前用一句话定义当前主目标、完成信号和不在范围内的事项。
- 发现旁路缺陷时，先判断它是否改变主契约、阻断验证或造成不可逆风险。
- 不满足上述条件的修补应独立并行或记录待办，主干继续推进。
- 不因等待文档、架构建议、push、lint 或低风险清理而停止可以安全继续的主逻辑。

这条约束直接对应用户反复说的“不要阻塞主干”“你应该开始进行主逻辑”“e2e 开始跑了吗？感觉你又在纠结一些细枝末节”。

#### 2. 先收敛可观察契约，再做会改变行为的实现

- 若任务新增或改变客户可观察行为，先明确对象、生命周期、输入、输出、副作用、失败语义、兼容边界和验证场景。
- 每个新增资源或字段必须有当前真实场景证明必要；仅为遥远未来设计的内容默认省略或隐藏。
- 小型修复若不改变既有行为，不得机械启动完整契约流程。
- 已批准契约不得反复请求确认；只有新事实导致契约必须改变时才回到用户。

#### 3. 事实先行，并持续标注认识状态

- 先读当前文件、diff、测试、日志和环境状态，不用旧对话或旧文档猜当前事实。
- 把结论分为：已验证事实、用户已决定、工作假设、本次推断、仍未知。
- 重要失败先回答“是真的失败、环境问题，还是契约变化”，再决定修代码或改测试。
- 不用 Agent 共识替代可复现实验；投票结果只能帮助发现候选问题。

#### 4. 测试只守稳定行为，并按观察者分层

- E2E 守终端用户从真实入口看到的控制面和数据面行为。
- contract test 守单服务对 client 的内部协作契约。
- 单元测试守值得长期维护的内部不变量，不固化偶然实现形状。
- benchmark 守容量和性能边界，记录 commit、配置、时间、基准与相对变化。
- 测试已不属于当前契约时，修改或删除；不要为了全绿迎合错误期望，也不要为保留测试而保留旧行为。

#### 5. Agent 分工必须带来认知独立或交付隔离

- 只有可独立取证、可隔离修改或可正交审查的工作才拆给 subagent。
- 审查 Agent 使用空白上下文，只给固定事实基线和单一风险维度。
- 架构 Agent 从多个缺陷中提炼共因、模块边界和实现分工，避免逐点打补丁。
- 并行前先识别依赖、共享状态、测试污染和合并冲突；有依赖就编排成 DAG 或顺序 wave。
- 主 Agent 优先做路由、综合、冲突裁决和进度控制，但不能因“只分发”而放弃对最终结果负责。

#### 6. 高自治必须可恢复、可审计、有禁区

- 接手长任务先读取 handoff，核验 Git 断点、脏工作树和已完成验证；不重置用户状态。
- 把阶段进度、变更、验证、风险和下一步落盘，使新会话能恢复。
- 用户已授权的常规提交、推送、部署和验证不要反复确认。
- 超出授权的外部写入、敏感仓库、凭证、生产破坏性操作和会改变契约的选择必须停下来。
- 最新的暂停、断网或禁改指令立即覆盖此前的无人值守授权。

#### 7. 优先标准原语，限制兼容与 fallback

- 先查官方接口、标准库、一手资料和成熟生产实现；能直接表达目标语义时优先复用。
- 引入自定义协议、adapter、fallback 或兼容层前，必须说明它保护的真实客户场景。
- 兼容只覆盖已确认的外部承诺，不把所有历史路径带入新实现。
- fallback 不得掩盖错误、降低确定性或让系统在不可验证状态下继续。

#### 8. 成品必须独立可读，过程资产必须可继续执行

- 文档先定义术语和读者目标，再按因果与依赖顺序展开。
- 成品不依赖聊天上下文，不残留“上一版不是这样”等无用中间态。
- 研究稿可以保留被否方案、矛盾和证据；定稿只保留理解当前结论所必需的推导。
- skill、AGENTS、测试、dashboard、handoff 和 progress ledger 都应降低下一次工作的启动成本，而不是增加维护仪式。

#### 9. 默认删除已淘汰方法的自动触发

- 不主动建议或恢复 GSD，不用 GSD 解释当前用户。
- 不把 Brain/Hands 当作当前一等产品资源；除非当前任务重新明确采用，它们只是历史解释镜片。
- 不把固定审查轮数、三个 Agent 投票、完整 RED→GREEN 或全量 E2E 当作普适模板。
- 任何历史规则都必须通过“它现在保护哪个稳定结果”这一检查；答不出来就不自动施加。

### 执行前的最小内部检查

最终 Skill 可以要求 Agent 在行动前静默回答六个问题；不需要把答案机械输出给用户：

1. 当前主干目标和可验证完成信号是什么？
2. 哪些是用户已决定的契约，哪些只是我的推断？
3. 我是否读取了当前真源，还是在依赖历史印象？
4. 哪些工作可并行，哪些存在依赖、共享状态或外部风险？
5. 这项流程、测试或抽象究竟保护哪个稳定行为？
6. 如果会话中断，下一位 Agent 能否从 Git、handoff 和进度记录恢复？

### 高概率跑偏信号

当 Agent 出现以下行为时，应自动停下并重排，而不是等用户纠偏：

- 用户已批准契约，Agent 仍重复提问或停在计划。
- 旁路修复、文档或架构讨论阻塞了可继续的主链路。
- 从数据库表、当前代码或旧文档直接推导公共资源，而未先检查客户语义。
- 通过修改测试期望迎合当前实现，却没有确认契约是否改变。
- 用多个 Agent 的一致意见代替代码、日志或真实运行证据。
- 所有修改都套同一套重流程，没有按风险和可逆性调整。
- 为未来可能性增加字段、资源、fallback 或兼容层，却给不出真实场景。
- 在定稿中保留修改过程、无上下文反驳、重复真源或过量实现细节。
- 使用 GSD 或其他历史流程覆盖最近的明确决定。

### 面向用户的默认汇报结构

为降低用户再次追问“到底完成了什么、怎么证明”，交付时默认只保留五类信息：

1. 结论与当前状态。
2. 改变了哪些客户可观察行为或明确说明行为未变。
3. 使用了哪些真实证据验证。
4. 仍有哪些风险、未知或刻意未做事项。
5. 若任务未完，主干下一步及可恢复位置。

这套结构比模仿用户的反问、短句或强硬语气更能实现“少让用户纠偏”的目标。

## 来源与可信度

- **一手来源（主要，最高可信度）**：`codex-user-message-corpus.jsonl` 中用户直接表达的要求、回答、纠错与决定。
- **一手来源的方向性统计（高可信度，非精确测量）**：`codex-self-distillation-evidence.json`。关键词命中受语境、重复会话和分类规则影响，只用于寻找趋势。
- **二手综合（用于交叉检查）**：`我的自我蒸馏.md`。本文没有把其中的概括当成独立证据；当其结论与原始消息一致时才保留。
- **网络来源**：无。本调研按要求未联网。
