# 他者视角与批评：来自 Codex 对话的行为反证

> 调研日期：2026-08-13  
> 调研性质：自我蒸馏的替代性“他者视角”  
> 证据范围：2026-03-16 至 2026-08-13 的 Codex 用户侧对话；当前判断重点采用近 30 天证据  
> 可信度说明：这不是同事评价、传记或心理测评。它只分析用户在委派任务、纠正 Agent、修改流程和验收结果时留下的可观察行为。

## 结论摘要

对话里最稳定的外部可见模式是：用户会给 Agent 很大的执行权限，但不会把判断权一并交出去。Agent 一旦混淆产品语义、扩大审查范围、凭空补设计、误读当前状态，用户通常会迅速收紧边界，要求回到代码、契约、真实环境或一手资料。

这既构成优势，也构成反证。优势是用户能识别“表面完整但语义错误”的产出；反证是很多关键约束仍保存在用户脑中，往往要等 Agent 走偏后才显式化。重复启动相同任务、反复要求继续、重新限定范围，不能直接证明执行失败，但至少说明当前 Agent 协作系统仍有较高的上下文恢复和监督成本。

最近最重要的成长证据是用户在 2026-08-13 明确表示“已经不用 GSD 了”。历史上对 GSD 的高频使用不应再被解释为当前身份。更准确的变化是：用户保留了语义收敛、阶段交接、独立验证和状态恢复等结果约束，同时开始主动删除过重流程，强调“小修并行、不能阻塞主线”。

## 一、证据方法与边界

### 1. 证据是什么

- **观察**：可以直接从用户消息、重复任务统计或时间窗口统计中读到的行为。
- **推断**：由多个观察共同支持，但用户没有直接说出的解释。
- **没有证据**：现有 Codex 对话无法支持的结论；不得用工作行为外推完整人格。

本次基础语料包含 4,169 份 rollout 记录，清洗后纳入 636 个用户侧会话、12,191 条用户消息，其中近 30 天有 108 个会话。当前特征采用 30 天半衰期；旧证据只用于说明稳定模式和变化轨迹。

### 2. 这不是严格意义上的“他者评价”

没有同事、下属、上级、客户或亲友对用户的独立描述，也没有访谈或 360 度反馈。因此本文不能回答“别人实际如何感受用户”。Codex 的回复也没有纳入语料，无法判断用户的每次纠正是否客观正确，只能确认用户确实进行了纠正，以及纠正所指向的质量标准。

### 3. 可信度分层

| 证据 | 可支持的结论 | 可信度 |
|---|---|---|
| 用户明确指令与明确否决 | 当时的目标、边界与偏好 | 高 |
| 同类纠正在多个任务中复现 | 稳定的工作判断模式 | 中高 |
| 同一首条 prompt 重复出现 | 任务被再次发起 | 高 |
| 重复出现的原因 | 可能是重试、并行验证、会话恢复或不满意 | 低；无法区分 |
| 对同事的影响、领导风格、情绪特征 | 无独立他者材料 | 没有证据 |

## 二、用户反复纠正 Agent 的地方

### 1. Agent 从错误语义出发时，用户会优先纠正“对象是什么”

**观察**

- 2026-07-15，Agent 将 runtime 不足解释为返回 429，用户纠正为“应该创建一个新的”，指出原解释不符合场景语义。
- 2026-08-02 至 08-03 的 API 设计讨论中，用户连续质疑 `InvocationPort`、`AgentType=CLOUD/EXTERNAL`、`ActivateAgentVersion`、`ResolvedImage`、`revision`、`Endpoint` 等命名或资源边界，并多次要求先看 AWS、Google 等实际设计，再讨论目标态。
- 2026-08-07，用户反复区分“租约”与“请求”、Stop 与 Delete、对外契约与内部实现、公开文档与未公开能力；当 Debug Endpoint 被设计成复杂框架时，用户要求回到“原子能力”和可组合 interface。

**推断**

用户对“实现是否能跑”的容忍度高于对“概念是否定义错”的容忍度。命名、所有权、生命周期和资源边界在用户眼里不是包装层，而是后续实现能否长期成立的前提。

**批评性反证**

这些约束经常在 Agent 给出方案后才通过连续追问显式化。也就是说，用户擅长识别错误模型，但未必总能在任务开始前把自己的领域模型完整外化。结果可能是：Agent 先生成一轮错误抽象，用户再通过高密度纠偏把它拉回正轨。

### 2. Agent 越过范围时，用户会把问题重新压回“本次变化”

**观察**

- 2026-07-28 至 07-29 的分支审查中，用户明确要求只审查当前分支引入的问题，不把 develop 已存在且合理的行为当作本次缺陷；之后逐条剔除“合理、可接受、无需报告”的项目。
- 2026-08-04，用户指出某分支主干“应该只增加 `docs/yunapi/v2`，其它都不要”。
- 2026-08-06，用户要求审查结果只保留 P0/P1/P2、问题位置、逻辑和建议，随后又要求“不要再跑全量测试了，只分析代码”。
- 2026-08-07，用户要求不要过度考虑非正常使用路径，并指出有些日志、trace、监控规范没有必要修改，应尽量原样复用。
- 2026-08-13，用户要求先合并一个不带 `cookbook/` 的版本，同时不能动本地文件。

**推断**

用户并不把“发现更多问题”等同于“更高质量”。他要求问题与当前 diff、当前契约和当前交付目标存在因果关系；对无关正确性、历史债务和提前设计有较强的排斥。

**批评性反证**

用户对范围的真实排序可能只有在审查结果出现后才完全显现。若任务入口只写“全面审查”，而后续又排除存量行为、可接受风险和非正常路径，Agent 很容易把“全面”理解为无限扩张。更低成本的做法需要在开跑前同时写清：比较基线、只报告何种新增风险、哪些风险已接受、哪些证据不得使用。

### 3. Agent 凭空补全或主观臆测时，用户会要求回到证据

**观察**

- 2026-07-15，用户要求日报不要主观臆测风险，并明确当日“风险、待跟进、明日计划”并不存在。
- 2026-07-16 至 07-17，用户指出 `examples/strands/FLOW.md` 是过时的假材料，要求不要被当前实现和 cookbook 误导，要使用外部一手资料和竞品证据。
- 2026-07-17，用户要求“不要生造词”，应使用权威定义；还要求文档解释参考了谁、为何如此设计。
- 2026-08-02 至 08-03，用户反复要求“每个都要有参考的目标，不要凭空设计和设想”，并要求先展示原厂字段，不要直接给改造结论。
- 2026-08-04，用户明确说明 CLI 和 SDK 尚未按最新 API 实现，因此不能声称已经验证。

**推断**

用户尤其警惕两类“看起来专业”的幻觉：一是用过时仓库材料冒充产品事实，二是把合理猜测写成已经验证的现状。其可信度标准不是引用数量，而是来源是否一手、是否适用于当前版本、结论是否超过证据边界。

**批评性反证**

用户也会在对话中提出自己的初步判断，例如“这个应该还好？”“是不是只要改……？”这些是探索性假设，不等于已验证事实。若 Agent 过度顺从，可能把用户的试探直接固化成结论。因此，真正符合用户标准的协作不是附和，而是把用户假设也放回代码和运行证据中验证。

### 4. Agent 停在中间状态时，用户会重复要求继续或恢复

**观察**

- 全量历史中，同一首条任务“拉取最新的 feat/agent-api 并合并到当前分支”出现 11 次；“详细说明 custom registry 逻辑”出现 7 次；“对比 develop 分支分析修改”出现 6 次。
- 近 30 天出现多次“继续”“别停下来”“重新跑”“拉取最新再看”，以及读取 pause handoff 后继续无人值守开发的请求。
- 2026-08-07 和 08-11 至 08-12，用户明确要求持续记录进度、按交接文档恢复、契约已经批准后不要再次确认，并要求正常情况下直接提交、推送、部署和验证。
- 用户在 2026-08-06 明确指出：让独立 subagent 执行代码修改，是为了防止主 Agent 上下文压缩导致流程丢失。

**推断**

用户非常重视任务连续性，并已把“上下文可能丢失”当作系统故障模式，而不是偶发体验问题。handoff、progress ledger、独立实现 Agent 和重复验证，都是对这一故障模式的工程化补偿。

**没有证据**

重复首条 prompt 不能证明 Agent 上一次失败，也不能证明用户缺乏耐心。它可能来自新会话重启、不同分支重复执行、并行取证或产品日志重复。只能确认：相同意图被多次重新发起，现有数据不能可靠解释原因。

## 三、被后续否决或降级的流程与资产

### 1. GSD：从高频实验变成明确淘汰项

**观察**

- GSD 相关会话在 31–60 天窗口覆盖 88/288 个会话（30.56%），近 30 天仅覆盖 1/108 个会话（0.93%）。
- 历史中同一 `gsd-do` 首条 prompt 出现 6 次，说明它曾是高频工作方式。
- 2026-08-13，用户明确说“我已经不用 gsd 了”。

**结论**

GSD 只可用于解释历史阶段，不得作为当前偏好或身份标签。当前保留的是它曾保护的结果：讨论与契约先行、阶段可恢复、实现后验证；被否决的是把固定阶段流本身当作正确性的做法。

**成长意义**

这是“方法忠诚”转向“结果忠诚”的直接证据。用户不是简单减少流程，而是在区分哪些约束真正降低失败概率，哪些仪式只增加等待和上下文成本。

### 2. 过时测试、路径和文档会被主动清除

**观察**

- 2026-07-15，EndpointSlice 路径被用户明确标记为废弃，不再考虑。
- 2026-07-16 至 07-17，旧 `FLOW.md` 被判为虚假、过时；cookbook 在产品基础推导中被判为不可信，不能反向约束 foundations。
- 2026-08-11，用户认为 integration test skills 已经无用，要求整理并用 e2e 补全 contract test 能力。
- 2026-08-12，用户要求优化 `develop-from-contract`：效率优先，小修交给 subagent 独立处理，不阻塞主干，并特意要求不要用该 skill 自己的流程修改它。

**推断**

用户愿意建设资产，也愿意否定自己过去建设的资产。资产是否保留，取决于它是否仍代表真实系统、是否降低下一次成本，而不是是否曾投入大量精力。

**风险提示**

快速淘汰是健康的，但也意味着文档、skills 和测试的维护成本可能被低估。如果资产创建速度长期高于验证、归档和删除速度，下一轮 Agent 会从过时材料中继续生成错误判断。用户已经看到这个风险，但目前没有证据表明所有仓库都有系统化的失效标记和清理机制。

## 四、相互拉扯的偏好

这些不是性格矛盾，而是需要显式调度的工程张力。若不写出优先级，Agent 会只执行其中一半。

### 1. 全面验证 vs. 效率优先

**观察**

一方面，用户要求 contract、lint、双审、预发布控制面、公网数据面 E2E、压测和可观测性检查；另一方面，又会要求不跑无关全量测试、删除冗余 lint、小修并行、不要阻塞主干。

**推断**

真实偏好不是“验证越多越好”，而是验证强度应与风险、影响面和可逆性匹配。问题在于这条分级规则尚未总在任务入口中结构化表达，所以 Agent 可能先执行最大验证集合，再被用户叫停。

### 2. 高度自治 vs. 精确边界

**观察**

用户允许无人值守开发、提交、推送、部署和验证，并要求已批准契约不要反复确认；同时会明确“不动 secrets 仓库”“不重置脏工作树”“不要动逻辑代码”“只改当前分支引入的问题”“不要动本地文件”。

**推断**

用户授权的是边界内执行，不是开放式处置权。协作者如果只看到“无人值守”，会低估禁区；只看到大量禁区，又会过度请示。理想协议应同时包含目标、可自主动作、禁止动作和停止条件。

### 3. 多 Agent 独立审查 vs. 不迷信多数票

**观察**

近 30 天，“并行与独立审查”标记覆盖 47/108 个会话（43.52%），明显高于 31–60 天的 12.50%。用户要求空白上下文、按风险维度拆分、独立取证，有时要求投票；同时又不断亲自追问具体缺陷是否真由本次变更引入，并剔除缺乏因果关系的结论。

**推断**

用户真正需要的是认知独立性，而不是 Agent 数量。多个 Agent 若共享同一模型偏见、错误基线或模糊任务边界，会产生相关性很高的假共识。对话显示用户正在从“多票更可信”转向“正交视角 + 可复现实验更可信”，但“投票”仍偶尔作为流程词出现。

### 4. 产品目标态 vs. 当前可运行事实

**观察**

用户会要求官方文档写目标态、尚未实现的功能先不暴露；也会要求 E2E、真实创建、现场录制和预发布验证来证明当前能力。用户还明确提醒“CLI 和 SDK 尚未实现，不能验证”。

**推断**

用户同时维护两套真相：产品应成为什么，以及系统今天实际能做什么。二者都合理，但文档若不显式标记目标态、已实现、已验证和暂不公开，就容易产生“文档正确但产品不可用”或“当前实现反向绑架长期设计”的冲突。

### 5. 完整表达 vs. 删除多余内容

**观察**

用户要求文档独立可读、来源明确、图示丰富、场景全面；同时频繁要求删除“多余”“不用说”“其它内容不要出现”的段落，并批评文档太多、太散、太复杂。

**推断**

用户要的不是篇幅完整，而是因果完整：关键语义、证据和决策不能缺失，但不能把探索过程、被否决方案和无关背景留在定稿中。Agent 容易把“完整”误解为堆料，这正是用户反复压缩内容的原因。

## 五、可能被本人低估的风险

以下均为推断，不是已经发生的事故结论。

### 1. 关键知识仍高度集中在用户本人

用户能快速指出 `FLOW.md` 过时、某接口属于另一产品线、某路径早已废弃、某风险可接受、某环境已经导入配置。这说明其领域记忆很强，也说明许多决定只有用户能即时判真。当用户离线或 Agent 无法访问完整上下文时，系统可能退回过时资料。

风险不只是“文档不够多”，而是权威性与时效性不够显式：哪个文档是目标态，哪个配置是当前事实，哪项风险已经接受，哪条路径已废弃。继续增加文档而不建立明确的真源和失效机制，反而会扩大误导面。

### 2. 高授权与凭证暴露面

对话中存在提交、推送、部署、集群操作、内部仓库和凭证相关配置的广泛授权。虽然本次输出已脱敏，但原始 Codex 日志仍可能保留敏感内容。用户对执行效率和无人值守的追求，可能让“最小权限、短期凭证、日志留存范围、外部写入审批”落后于自动化能力增长。

没有证据表明已发生泄露或越权；风险来自授权半径与可留痕数据同时扩大。

### 3. 多 Agent 可能放大同源偏差与协调成本

空白上下文能降低相互影响，却不能保证模型、提示和比较基线真正独立。每个小问题都启动多个 Agent、再汇总、再投票，会产生新的延迟、重复阅读和冲突消解成本。用户已经用“小修并行、不阻塞主线”回应这一问题，但还没有证据显示验证强度已经形成稳定、可复用的分级规则。

### 4. E2E 真源可能挤压其它证据层

用户正确地用 E2E 锚定客户可观察行为，但 E2E 不擅长定位局部不变量、穷举竞态或稳定覆盖所有失败组合。近期用户也会在适当场景要求“只静态分析，不跑全量测试”，说明其正在区分证据类型。仍需警惕把“真实环境通过”误写成“所有内部语义都正确”。

### 5. 高密度纠偏可能掩盖任务入口质量问题

用户能在几轮内把 Agent 拉回正确方向，因此单次纠偏看起来成本不高。但在长任务中，多个“不是这个”“只改这些”“不要过度设计”会累积成显著返工。若一个约束已经重复纠正过，它就不应继续只存在于个人记忆中，而应进入契约、AGENTS.md、skill 或任务模板。

### 6. 快速演进会使昨天的“最佳实践”成为今天的错误先验

GSD 的淘汰是最明确案例。类似地，旧 integration skills、旧流程图、旧 endpoint 路径和 cookbook 也被陆续降级。用户的成长速度意味着“历史频次高”并不等于“当前置信度高”。任何长期记忆系统若只做频次统计、不做时间衰减和明确否决覆盖，就会持续把过去的用户强加给现在的用户。

## 六、对未来 Agent 的负面校准

以下规则不是对用户偏好的重复赞美，而是从失败和纠偏中提炼的防错要求：

1. 不要用历史高频覆盖最新明确决定。GSD 已于 2026-08-13 被用户明确淘汰。
2. “全面”不等于无边界。先确认比较基线、当前 diff、已接受风险和不在范围内事项。
3. 不要把用户的探索性问句当作决策；用代码、运行数据或一手资料验证。
4. 不要用当前实现反向定义产品，也不要用目标态冒充当前已实现能力；两种状态要明确标记。
5. 多 Agent 的价值来自独立证据和正交视角，不来自票数本身。
6. 用户说“无人值守”时，仍要严格遵守其列出的仓库、工作树、凭证和外部写入边界。
7. 一个约束若被用户纠正两次，应把它固化到可继承资产，而不是期待下一次会话记住。
8. 验证应按风险分层：E2E 守客户契约，组件/契约测试守协作边界，单元测试守稳定内部不变量，静态分析用于限定 diff 和代码路径。
9. 最终文档应保留因果链与证据，删除探索过程和被否决方案；“完整”不是篇幅长。
10. 当用户的最新判断与旧文档冲突时，先指出冲突和证据时间，再以最新明确决定为准。

## 七、没有证据支持的结论

现有材料不足以判断以下事项：

- 用户在工作之外的性格、情绪结构、生活偏好和关系模式。
- 同事是否认为用户“要求高”“难合作”或“值得信赖”；没有真实他者访谈。
- 用户每次技术判断是否最终正确；语料没有系统收录 Agent 回答、代码结果和事后复盘。
- 重复任务究竟源于 Agent 失败、用户主动并行、跨分支重复、会话重启还是日志重复。
- 多 Agent 流程总体节省还是增加了时间与成本；没有统一的交付周期和质量基线数据。
- 用户是否已经在组织层面解决知识集中、权限治理和资产失效问题；对话只显示其意识和局部行动。

## 八、可供后续提炼的核心张力

1. **把执行委派出去，但不把语义判断委派出去。**
2. **相信真实运行结果，但不让 E2E 成为唯一证据。**
3. **建设流程来对抗遗忘，又持续删除反客为主的流程。**
4. **要求全面覆盖，同时要求每一项都与当前目标有因果关系。**
5. **追求无人值守，同时用精确禁区控制外部影响面。**
6. **依赖多 Agent 获得认知独立性，同时必须防止同源假共识。**

这些张力比单一标签更能解释用户当前的工作方式。它们不是需要被消除的矛盾，而是未来 Skill 回答问题时应主动权衡的变量。

## 九、可前置的防漂移门槛

这组门槛的目的不是增加一套新仪式，而是把已经反复发生的人工纠偏前移。Agent 应在内部完成检查；全部能由代码、文档和现有决定回答的问题，不得重新询问用户。

### 1. 行动前：确认没有从错误世界模型出发

- **最新决定优先**：是否检查过最近指令对历史做法的明确覆盖？尤其不得再把 GSD 当作当前默认流程。
- **对象语义明确**：核心对象、所有权、生命周期、状态和失败语义是否已从契约或一手材料确认，而不是从名称猜测？
- **真源有效**：使用的代码、文档、配置和竞品资料是否仍有效？是否把目标态、当前实现、已验证能力和暂不公开能力分开？
- **范围可判定**：比较基线、目标 diff、允许修改范围、明确禁区和停止条件是否清楚？“全面”不得被解释为处理所有历史问题。
- **用户陈述的状态正确**：是否区分了用户的明确决定与探索性问句？“是不是”“我觉得”提出的假设仍需验证。
- **验证强度匹配风险**：是否根据影响面、可逆性和失败代价选择静态分析、单元测试、contract test 或 E2E，而不是默认全套流程？

若以上任一项缺失，先从现有材料补齐。只有缺口会实质改变契约、授权范围或外部影响时，才向用户提出一个必要问题。

### 2. 执行中：持续证明没有越界或被流程带跑

- **每项工作都能回指目标**：当前修改、调研或测试能否说明它如何服务本次契约？不能说明的先暂停，不把顺手发现的历史债务并入主线。
- **新事实改变计划时及时收敛**：发现文档过时、代码与假设不符或用户已修复问题时，应重读当前状态并更新计划，不沿用旧结论继续做。
- **主线与小修分离**：可独立交付的小问题交给独立执行单元，不阻塞主线；但不得借“并行”扩大未经授权的修改面。
- **结论靠证据而非票数**：多 Agent 意见一致仍需代码路径、diff、测试或运行数据支持；冲突时比较证据质量，不以多数决制造确定性。
- **保留用户状态与禁区**：不重置脏工作树、不改未授权仓库、不碰凭证边界、不移动用户要求保留的本地内容。
- **进度可恢复**：长任务的已完成项、当前断点、验证证据和剩余风险是否及时落盘，避免靠聊天上下文维持连续性？
- **流程成本不过量**：如果流程本身开始延迟交付，是否可以保留结果约束、压缩仪式步骤？不得为了忠实执行某个 skill 而牺牲任务目标。

### 3. 交付前：防止“看起来完成”替代真实完成

- **事实状态准确**：有没有把未实现写成已实现、把未验证写成已验证、把用户假设写成事实、把历史偏好写成当前偏好？
- **变更范围准确**：最终结果是否只包含本次需要的修改？是否混入无关重构、过时路径、被否决方案或不属于本产品线的内容？
- **验证与声明对齐**：每个“通过”“修复”“兼容”“可用”是否有对应证据；没有测到的边界是否明确写出？
- **对外与内部信息分层**：对客内容是否泄露底层实现、内部地址、凭证或未公开能力？内部记录是否又因过度脱敏而失去排障价值？
- **文档因果完整且不过载**：读者能否看懂目标、事实、约束、决策和效果；探索过程、无关背景和“其实没有定义”的省略项是否已删除？
- **本地与外部状态一致**：提交、推送、部署、工作树和远端分支分别处于什么状态，是否经过核验而非假定？
- **残余风险诚实**：是否区分已修复问题、接受风险、待验证事项和没有证据的推断？

### 门槛的通过标准

Agent 只有在三组检查均无实质缺口时，才应把任务报告为完成。检查结果默认不需要逐项展示给用户；最终只需报告结论、关键证据、实际验证、刻意保留项和残余风险。若同一种纠偏再次发生，应优先更新契约、AGENTS.md、skill 或任务模板，使下一次在行动前自动拦截，而不是把“用户还会纠正”当作质量保障。
