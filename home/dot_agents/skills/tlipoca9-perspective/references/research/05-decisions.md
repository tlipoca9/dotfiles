# 05｜重大决策与行动：从 Codex 对话反推判断机制

## 结论先行

用户近期的实际决定呈现出一套相当稳定、但正在变轻的工程判断机制：先确定客户可观察语义和系统边界，再把它冻结为可验证契约；执行阶段可以高度委派并无人值守，但必须以真实环境、E2E、benchmark、日志和代码状态闭环；兼容性只保护被明确选中的外部承诺，不保护历史实现本身；流程如果不能直接降低交付风险，就应被删掉、延后或并行化。

这不是“严格”与“效率”的二选一。更准确的描述是：**对结果严格，对仪式节制；对边界精确，对执行放权；对历史有选择地继承，对新证据随时开放修正。**

以下判断采用 30 天时间衰减：2026-07-14 至 2026-08-13 的直接指令权重最高，更早记录只用于确认是否跨场景复现。2026-08-13 用户明确声明“我已经不用 gsd 了”，因此 GSD 只作为被替换的历史流程，不计入当前偏好。

## 证据口径

- **一手材料**：`codex-user-message-corpus.jsonl` 中可明确识别为用户本人作出的指令、纠偏、批准或拒绝。
- **辅助材料**：`codex-self-distillation-evidence.json` 用于确认时间窗口和重复频率；`我的自我蒸馏.md` 只作为待核验的二手总结，不单独支撑结论。
- **行为证据**：用户跨会话反复选择同一种做法，例如持续要求真实部署后跑 E2E，权重高于一次性的自我描述。
- **结果边界**：语料主要记录用户请求，不完整包含工具执行结果。除非后续用户消息明确确认结果，否则本文只记录“决定已作出”或“工作持续推进”，不把计划冒充已完成事实。
- **污染控制**：语料中可能包含用户粘贴回来的助手文本。本文只使用具有明确第一人称意图的短指令与纠偏，不把长篇复述自动视为用户自述。

## 决策 1：先从资源本质推导契约，但冻结契约不等于禁止复核

### 背景

Deployment 的产品语义、API、数据结构和运行时行为正在收敛。一个风险是从现有数据库表、内部控制器或过往实现反推新资源；另一个风险是契约一经讨论就被当作不可质疑的文本，导致不必要的字段和机制进入最终设计。

### 选择

用户选择先回答“Deployment 是什么、应呈现什么行为”，再自然推导契约和架构；对进入开发阶段的已批准契约，不允许执行 Agent 反复请求确认，但仍允许在有本质理由时修订具体语义。

### 一手证据：用户明确说了什么

- 2026-08-10 要求“从定义推导到契约”，并要求“从本质推导我们的契约行为是否合理，不要预设契约是神圣的”；随后删除了认为没有必要的 `ResourceVersion` / `ObservedResourceVersion`，把 `FAIL_OVER` 改名为 `STRICT`。（语料：会话 `019feb08-93c1-7161-b3ee-c2659b89b54a`，消息 7–13）
- 2026-08-11 在开发已开始后明确：“契约不要再问我”，但同一会话又把 `BEST_EFFORT` 对非法 affinity id 的行为修改为 fail-open。（语料：会话 `019ff13a-e6a8-7300-b16a-a8d381434b6e`，消息 6、9–10）
- 2026-08-12 对 CLI 契约给出明确批准，随后仍要求实现不要把生成代码复杂化，问题应回到生成器解决。（语料：会话 `019ff4b1-5c94-7473-90bb-b7135399d657`，消息 19–22）

### 实际反复采取的行动

用户不是先维护“冻结”的形式，而是先审视概念、删除多余字段、修正命名和失败语义；只有当语义收敛并批准后，才要求执行层停止重复确认并直接开发。这种顺序在 Deployment 架构文档、YunAPI v2 和 CLI 子命令三个场景中重复出现。

### 推测出的规则

> 如果一个决定仍处于语义设计阶段，就从用户可观察事实重新推导，契约也可以被质疑；如果契约已明确批准并进入实现阶段，就把它当作执行边界，除非出现新的行为证据或本质矛盾。

这解释了表面张力：用户既说“不要预设契约是神圣的”，又说“契约不要再问我”。前者针对设计质量，后者针对执行效率，并不矛盾。

### 结果或未知

Deployment 契约被明确批准并用于后续开发；部分语义在开发中继续小幅修正。本文无法仅从用户消息确认最终实现是否全部合入。

**置信度：高。** 近期同一项目中有连续、具体的选择和纠偏。

## 决策 2：兼容外部承诺，不兼容全部历史实现；决定删除时要彻底

### 背景

YunAPI v2 和 Deployment 引入新路径，同时存在 External Agent、旧 YunAPI、数据库存量和旧测试。全面兼容会把历史债务带入新实现；全面删除又可能破坏真实客户链路。

### 选择

用户把兼容范围缩到明确的客户承诺：External Agent 的外部契约和相关链路需要保留，底层可以转译到新的 Sandbox Instance Endpoint；数据库需要 migration；除此之外的旧 YunAPI 和存量 E2E 不承担默认兼容义务。被替换的内部实现则应清理干净，不留代码、注释、文档或测试残骸。

### 一手证据：用户明确说了什么

- 2026-08-07 要求实现 `docs/yunapi/v2`，同时保留 External Agent 对外契约；又明确“只有 external agent 的需要兼容，其它原有 yunapi 都不需要保证”，目的是避免历史债务迫使实现持续兼容。（语料：会话 `019fdb52-9b72-7ae0-9a02-a2e440533d33`，消息 1；会话 `019fdb5b-aeb1-7e63-b44d-d5628a8f4e0d`，消息 107、114、155–156）
- 2026-08-04 指出众安客户不感知 External Agent，他们真正依赖的是稳定服务入口、会话控制和实例调度；因此旧内部资源只是迁移目标，不是永久边界。（语料：会话 `019fcc98-f411-72f1-8566-4947119d32cf`，消息 24–27）
- 2026-08-12 要求以另一个 CLI 仓库内容替换当前项目，只复原新增的 `session` 子命令，“其它都是不需要的”；同日要求 MySQL claim 逻辑“不能有任何残留代码、注释、文档、测试”。（语料：会话 `019ff4b1-5c94-7473-90bb-b7135399d657`，消息 1；会话 `019ff66b-c6b1-7390-a22c-09064c49ce1a`，消息 24）
- 2026-08-13 希望先合并不带 `cookbook/` 的版本，但“不要动本地文件”，说明删除发布内容与丢弃本地工作不是同一件事。（语料：会话 `019ffa28-ef34-7953-acd7-4147e90d5475`，消息 1）

### 实际反复采取的行动

用户多次逐项划定“保留什么、丢弃什么、哪一层保留”：External Agent 保留外部行为而不保留内部实现；数据库保留可迁移性；旧 YunAPI、旧 E2E 和 MySQL claim 可删除；本地尚未发布的工作应继续保留。这比笼统地“向后兼容”更像一份承诺清单。

### 推测出的规则

> 兼容性的对象是被客户真实依赖的行为和数据，不是曾经存在过的代码路径。没有明确外部承诺的历史实现默认可删；一旦决定替换，残留本身就是认知和维护成本。

### 结果或未知

兼容边界已被反复明确，并被要求纳入 External Agent 回归与 benchmark。MySQL claim 是否已完全清理、旧 YunAPI 是否最终全部移除，语料中没有最终确认。

**置信度：高。** 决策覆盖 API、数据库、测试、CLI 和本地 Git 状态，且边界一致。

## 决策 3：把 E2E 当作客户契约真源，但不同测试层只保护各自值得保护的事实

### 背景

多服务系统同时存在单元测试、历史集成测试、contract test、根 E2E 和真实环境 benchmark。如果每一层都复制所有行为，会形成昂贵且脆弱的测试负担；如果只做内部测试，又无法证明客户链路可用。

### 选择

用户选择先写 E2E 场景，再实现代码和服务 contract test，最后构建部署到预发布环境并重新跑 E2E；每服务旧集成测试由 contract test 替代。测试只应固化长期稳定的行为，不应刻意保证任意数据形状。功能通过后，再用分场景 benchmark 验证容量和性能。

### 一手证据：用户明确说了什么

- 2026-08-07 直接定义“当前我们的契约协议为 e2e”，并规定链路：“先实现 e2e test，再实现开发代码和 contract test……构建镜像并部署，最后确保 e2e test 通过”；测试配置还必须落到可复现环境中。（语料：会话 `019fdb5b-aeb1-7e63-b44d-d5628a8f4e0d`，消息 1、154、169）
- 同日决定“每个服务的集成测试要被 contract test 替代”，且旧 E2E 只保留明确声明的 External Agent 兼容场景。（同会话，消息 93、155）
- 2026-08-11 拒绝 DB 测试刻意证明“第三条记录”和“非 24h 记录”可以落库，理由是这不是长期保证，容易变成无价值测试。（语料：会话 `019fefee-dbcc-71d2-b6f2-6782822d4655`，消息 7）
- 2026-08-11 至 12 要求在全部 E2E 通过后，对数据面做 0–50 实例、每 RS 100 并发、最高 5k QPS 的分场景 benchmark，并保留 External Agent 基线避免劣化。（语料：会话 `019ff13a-e6a8-7300-b16a-a8d381434b6e`，消息 4、27；会话 `019ff66b-c6b1-7390-a22c-09064c49ce1a`，消息 34–37）
- 2026-08-12 明确要求使用“真实可用的 deployment 接口”，录制前先验证所有不确定项，避免用演示替代真实行为。（语料：会话 `019ff4b1-5c94-7473-90bb-b7135399d657`，消息 22、130、134、178）

### 实际反复采取的行动

在 7 月至 8 月的多次任务中，用户持续要求构建镜像、部署重庆预发布、运行全量或专项 E2E、检查日志和资源，再针对失败继续定位；当使用错镜像、错域名、错环境或只展示理论结论时，会立即纠正。这比“重视测试”的口头表态更强：真实运行结果实际决定下一步。

### 推测出的规则

> 客户可观察语义由 E2E 守住；服务间协作由 contract test 守住；内部测试只守稳定不变量；容量结论必须由真实 benchmark 给出。任何一层都不应为了覆盖率而发明长期承诺。

### 结果或未知

测试层级和执行顺序已明确，并持续用于开发。语料显示 E2E 与 benchmark 正在反复运行和优化，但不能确认最终 5k QPS 目标已达到。

**置信度：高。** 跨月、跨仓库反复出现，且直接改变开发顺序。

## 决策 4：把复杂性放在更可演化的层；高并发状态的存储选择服从负载事实

### 背景

Deployment 开发中出现双槽数据库约束、手写 SQL、Token 缓存、租约释放和请求槽位等设计。某些方案能在数据库层快速“锁死”规则，却可能降低未来扩展性；另一些方案在低吞吐存储上承担高频协调，会直接成为性能瓶颈。

### 选择

用户拒绝把双槽等产品策略硬编码成数据库结构，倾向用代码与事务闭环，并优先使用 ORM 而不是扩散手写 SQL。对于高 QPS 槽位/排队状态，用户拒绝 MySQL，改用 Redis；对于异步租约释放，则通过多 worker、批量/定时触发和容量不足时的一次立即释放来削峰。

### 一手证据：用户明确说了什么

- 2026-08-11 质疑“双槽设计需要在数据库层面限制”，认为扩展性差，应通过事务保证；随后明确“复杂性不要搞到数据库层面，最好在代码层面闭环”，并要求评估能否用 ent 替代手写 SQL。（语料：会话 `019fefee-dbcc-71d2-b6f2-6782822d4655`，消息 3、6、8）
- 2026-08-11 为 Customs 异步 release 设计多 worker、`100ms` 或积累 `20` 个即释放，以及容量不足时立即释放并只重试一次，用来避免请求起止各调用一次 Berth 造成的 `2 × N` QPS。（语料：会话 `019ff13a-e6a8-7300-b16a-a8d381434b6e`，消息 12）
- 2026-08-12 发现槽位进入 MySQL 后直接否决：“不能用 redis 吗？”“mysql 肯定扛不住啊”，并要求彻底清理 MySQL claim 路径。（语料：会话 `019ff66b-c6b1-7390-a22c-09064c49ce1a`，消息 22–24）

### 实际反复采取的行动

用户没有抽象地坚持某种数据库或框架，而是根据变化频率和负载特征移动边界：长期数据可 migration，运行时策略放在代码，高频协调进入 Redis，外部调用通过批量化削峰。发现架构落点错误时，会要求把错误路径完整删除，而不是再加兼容层。

### 推测出的规则

> 稳定事实可以进入持久模型；易变策略应留在代码；高频瞬态协调使用适合吞吐的状态设施。不要为了局部确定性，把未来变化和热路径压力永久压进数据库。

### 结果或未知

Redis 方向被明确批准，MySQL claim 被要求清理；是否完成迁移以及在 5k QPS 下的最终表现仍未知。

**置信度：高。** 近期决定具体，且与后续清理和 benchmark 直接相连。

## 决策 5：Agent 分工的核心不是数量，而是边界、独立性和不阻塞

### 背景

复杂重构同时包含架构、实现、文档、故障定位、代码审查和性能验证。单 Agent 串行处理会拖慢主线；但多个 Agent 共享同一叙事，也可能复制同一个误判。

### 选择

用户把主 Agent 推向调度者角色：将可独立交付的缺陷、调研和验证交给边界清晰的 subagent；大型审查按缓存、资源、竞态等正交维度拆分，并要求每条结论归因到当前 diff；架构师必须负责代码架构设计，但架构工作不能阻塞主干测试和开发。

### 一手证据：用户明确说了什么

- 2026-07-24 对五个独立问题要求“每个问题一个 subagent”。（语料：会话 `019f93fe-7736-7401-a4a2-fc59673fe58f`，消息 46）
- 2026-07-28 要求 6 个 subagent 从缓存、资源创建、竞态和未知风险等不同方向审查；当结论混入 develop 已有行为后，又明确规定 `merge-base(origin/develop, HEAD)..HEAD` 为唯一范围，每条问题必须指出新增 diff 和因果链。（语料：会话 `019fa778-96eb-7651-afc1-9aa1eb411229`，消息 3–5；会话 `019fa78e-715c-7643-ae3f-6a15f4243460`，消息 2）
- 2026-08-11 说“主 agent 最好只做任务分发，不要直接调用工具”，并多次要求旁路问题由 subagent 自行验证，不要暂停主干。（语料：会话 `019fefee-dbcc-71d2-b6f2-6782822d4655`，消息 10–14、36、40–43）
- 2026-08-12 规定 single 与 brain-hands 两条架构隔离，分开 subagent group，彼此不要依赖；同日强调架构师应做最有软件工程含量的代码架构设计，但“架构师设计不能阻塞主干”。（语料：会话 `019ff4b1-5c94-7473-90bb-b7135399d657`，消息 44；会话 `019ff517-01a6-79e0-86b6-55744090abfb`，消息 7；会话 `019ff66b-c6b1-7390-a22c-09064c49ce1a`，消息 2–3、7）

### 实际反复采取的行动

用户不只口头赞成多 Agent，而是反复指定：任务数量、审查维度、唯一 diff 范围、是否允许修改、交付格式、失败返回条件和并行关系；还专门验证了自定义 `luna_worker` 是否真的能被原生 subagent 机制调用。说明他关心的是可验证的组织能力，而不是“开了几个窗口”。

### 推测出的规则

> 能定义清楚输入、输出和所有权的工作就委派；需要共同语义判断的主线由主 Agent 编排；审查 Agent 必须按不同风险维度独立取证；任何旁路任务都不应因等待、评审或工具调用阻塞主链路。

### 结果或未知

subagent-driven 已成为反复使用的工作方式，自定义 Agent 也被单独做过能力验证。各次委派的最终质量不在用户语料中完整可见。

**置信度：高。** 有大量真实调用指令，行为证据远强于自述。

## 决策 6：在目标和禁区明确后，授权 Agent 无人值守完成整条交付链

### 背景

长任务跨越多次断网、会话和人工休息，且工作树可能已有未提交内容。如果每一步都重新请求批准，交付链会被人为打断；如果完全无边界地自治，又会危及现有工作、凭证仓库和外部环境。

### 选择

用户授权 Agent 在批准契约后持续开发、测试、提交、推送、构建、部署和验证，并通过 handoff 与进度文档跨会话恢复；同时明确护栏：冻结脏工作树而非重置、按交接顺序核验 Git 断点、不修改指定 secrets 仓库、使用指定预发布地域和测试上限。

### 一手证据：用户明确说了什么

- 2026-08-07 进入“无人值守的开发自闭环”，要求所有需要人工确认的事项根据 Deployment 本质自行推导，并让独立 subagent 维护进度记录。（语料：会话 `019fdb5b-aeb1-7e63-b44d-d5628a8f4e0d`，消息 169）
- 2026-08-11 要求读取 handoff 后继续无人值守开发：“先冻结当前脏工作树，不重置”，再补测试、双审、提交、部署和 E2E，并持续写进度文件。（语料：会话 `019fefee-dbcc-71d2-b6f2-6782822d4655`，消息 1）
- 同日再次要求“推送吧，后面不要再问我了，这是无人值守的开发流程，我后面再看”。（语料：会话 `019ff13a-e6a8-7300-b16a-a8d381434b6e`，消息 13）
- 2026-08-12 的恢复指令同时包含高授权和精确禁区：正常情况下直接提交并代推，但不要修改指定 secrets 仓库；按 handoff 顺序恢复并完成 E2E 与 benchmark。（语料：会话 `019ff66b-c6b1-7390-a22c-09064c49ce1a`，消息 1）

### 实际反复采取的行动

用户多次在断网或暂停后用 handoff 恢复任务，并要求继续推送、部署、测试而不再次确认；但每次都带着环境、仓库、工作树和验证范围的边界。授权对象是闭环执行，不是重新定义目标或任意扩大外部影响面。

### 推测出的规则

> 一旦目标语义、可接受风险和禁区明确，Agent 应自行推进到可验证结果；确认应发生在边界变化时，而不是每个执行步骤。长期任务的连续性依靠可恢复状态，而不是依靠同一会话持续在线。

### 结果或未知

无人值守流程至少跨多个会话被恢复并继续，说明 handoff 机制实际投入使用；是否每条交付链都最终合并上线无法从本语料确认。

**置信度：高。** 多次真实授权与恢复行为一致。

## 决策 7：效率优先意味着删除或延后中间仪式，而不是降低最终证据标准

### 背景

严格的 contract、lint、双审、RED→GREEN、pre-commit、pre-push、完整兼容和多轮确认叠加后，可能让主干工作停在细枝末节。用户近期开始主动修正这种流程膨胀。

### 选择

用户要求能并行就并行，局部修补交给 subagent；非最终定稿不跑 pre-commit/pre-push，必要时先 `commit --no-verify`；benchmark 不套 RED→GREEN；可重建的预发布数据库和历史 Deployment 可以牺牲；但最终仍必须跑 E2E、benchmark，并记录每轮 commit、改动、基准和时间点。

### 一手证据：用户明确说了什么

- 2026-08-11 两次强调“效率优先”，小修不要阻塞主干；允许重庆数据库必要时重建，也允许丢弃历史 Deployment。（语料：会话 `019fefee-dbcc-71d2-b6f2-6782822d4655`，消息 9–10；会话 `019ff13a-e6a8-7300-b16a-a8d381434b6e`，消息 8、24）
- 2026-08-12 看到主线未开始时直接纠偏：“架构师设计不能阻塞主干”“你应该开始进行主逻辑呀，测试、发现问题、反馈”“e2e 开始跑了吗？感觉你又在纠结一些细枝末节的”。（语料：会话 `019ff66b-c6b1-7390-a22c-09064c49ce1a`，消息 2–3、11）
- 同一会话要求最终定稿前不跑 pre-commit/pre-push，benchmark 不需要 RED→GREEN；但随后规定 QPS 按倍增探测、失败后用二分法找基准，并逐轮记录 commit、优化和结果。（同会话，消息 18、31–37）
- 2026-08-12 要求把 `develop-from-contract` 简化，明确“不认为一个复杂的流程能适用于大多数情况”，但又拒绝过度删减到丢失核心。（语料：会话 `019ff517-01a6-79e0-86b6-55744090abfb`，消息 1–7）

### 实际反复采取的行动

用户会主动移除不产生新信息的门槛、减少重复校验、允许可逆环境重建，并持续催促先跑主流程；与此同时，对真实 E2E、性能基准、变更可追踪性和最终验证的要求没有下降，甚至更具体。

### 推测出的规则

> 先问每个步骤是否会改变当前决策或降低不可逆风险。不会的步骤就删、延后或旁路；会决定客户行为、容量上限或发布安全的证据必须保留。质量预算按风险分配，而不是平均铺给所有流程节点。

### 结果或未知

这一原则已写入 `develop-from-contract` 的修改诉求，并在实际任务中用于并行小修、延后 hook、简化 benchmark 流程。最终 skill 的具体形态不由本文判断。

**置信度：高，且是近期最强的变化信号。**

## 决策 8：文档是独立产品界面，不是聊天记录、仓库注释或实现过程的转储

### 背景

Deployment 同时有契约文档、接口文档、技术架构文档、Outline 页面和 cookbook。若作者把内部演进史、迁移说明、仓库路径或中间推理直接暴露给读者，文档会依赖作者上下文，用户无法据此理解和操作产品。

### 选择

用户要求最终文档从定义和用户旅程自然推导，按依赖顺序呈现概念；读者所需背景、术语、对象关系、生命周期、接口、约束和失败语义必须在正文自洽说明。现有接口、架构和契约文档只是作者侧事实来源，不应成为读者必须访问的依赖；未正式上线的迁移过程和“对冻结契约的复核”不进入首份正式技术文档。

### 一手证据：用户明确说了什么

- 2026-07-17 明确要求最终版本不能写成“改了几版”的历史叙事，并批评原产品基础文档“一堆中间说明，没有上下文的东西，多余的引用”。（语料：会话 `019fcc98-f411-72f1-8566-4947119d32cf`，消息 27；会话 `019f6f2b-a8b2-7fa1-a25c-0b6ed21a04b4`，消息 60）
- 2026-08-10 要求把首份 Deployment 技术文档当作独立终稿，不写迁移，按定义自然推导契约；拒绝把“对冻结契约的复核结论”放进技术架构正文。（语料：会话 `019feb08-93c1-7161-b3ee-c2659b89b54a`，消息 1、5–12）
- 2026-08-10 要求新增数据结构、接口和错误码按依赖顺序展示，无依赖者在前，并只展示新增错误码。（语料：会话 `019feb1d-ba65-7713-9288-28dafa30ca21`，消息 1）
- 2026-08-11 给文档 subagent 的完整委托明确：最终读者不知道当前仓库，所有必要内容必须在 Outline 正文讲清楚；接口、架构和契约文档“仅作为作者侧事实来源”，写后要重新读取并检查完整性和一致性。（语料：会话 `019fefee-dbcc-71d2-b6f2-6782822d4655`，消息 12；会话 `019ff020-73e1-7cf0-9a7b-975b7fd0136e`，消息 2–3）
- 2026-08-12 进一步要求 cookbook 的 README 必须是 step-by-step、完全可执行的操作，演示台本必须“是人看的”，真实但不暴露用户不关心的内部妥协。（语料：会话 `019ff4b1-5c94-7473-90bb-b7135399d657`，消息 25、32、81、99、130、171）

### 实际反复采取的行动

用户多次重写而不是小修文档，持续删除迁移史、中间说明、内部实现暴露和无上下文段落；同时要求示例、CLI、视频与真实用户路径互相验证。对文档的验收标准实际是“读者能否在没有作者陪同的情况下理解并执行”。

### 推测出的规则

> 文档必须按读者需要建立完整因果链；内部材料可以提供事实，但不能成为理解前提。实现历史只在会改变使用、迁移或风险判断时出现，其他内容应从最终产品语义中删除。

### 结果或未知

多个正式文档、Outline 与 cookbook 被要求按这一标准重写或验证。最终页面质量需要读取产物才能单独评估，本文不据请求推定其已达标。

**置信度：高。** 跨产品设计、技术架构、API、Outline 和演示资料复现。

## 决策 9：淘汰 GSD，保留它曾经保护的结果，并把流程替换为更轻的契约驱动协作

### 背景

更早阶段大量使用 GSD 式分阶段工作流。证据统计显示，它在 31–60 天窗口命中 88/288 个会话，而近 30 天仅命中 1/108；与此同时，近期对话转向 `develop-from-contract`、独立架构设计、subagent 并行和无人值守 handoff。

### 选择

用户已明确停止使用 GSD。当前保留的不是旧流程名称和完整仪式，而是少数仍有价值的结果约束：语义先收敛、已批准契约可执行、状态可恢复、实现必须经真实验证、独立问题可以并行。

### 一手证据：用户明确说了什么

- 2026-08-13：“我已经不用 gsd 了。”并要求蒸馏时理解“最近的对话置信度越高，人是会成长的”。（语料：会话 `019ffae9-2b43-7f82-83c3-6f979e2e487f`，消息 2–3）
- 2026-08-12 要求精简 `develop-from-contract`，认为复杂流程不适用于大多数情况；但当精简过度时，又要求保留真正的核心和架构师的代码架构职责。（语料：会话 `019ff517-01a6-79e0-86b6-55744090abfb`，消息 1–7）
- 2026-08-11 至 12 的实际工作已采用“契约批准后不再确认 + 小修并行 + handoff 恢复 + E2E/benchmark 收尾”，而不是 GSD 阶段命令。（语料：会话 `019ff13a-e6a8-7300-b16a-a8d381434b6e`，消息 8–13；会话 `019ff66b-c6b1-7390-a22c-09064c49ce1a`，消息 1–3）

### 实际反复采取的行动

近 30 天的行为不是简单换名：用户持续删减不必要的检查、拒绝流程阻塞、强化主干优先和风险分层；同时保留契约、交接、独立审查和真实验证。这表明淘汰对象是流程壳，而不是工程纪律。

### 推测出的规则

> 方法论是暂时工具，不是身份。先把流程推到足够深，确认它真正保护的结果，再把无效仪式删掉；新指令和新行为应覆盖旧标签。

### 结果或未知

GSD 已被用户明确判定为过时，不应出现在当前人物 Skill 的触发词、身份描述或工作流中。可以作为成长轨迹中的历史实验出现，但必须标注“已淘汰”。

**置信度：最高。** 有最新直接声明，并得到使用频率变化与替代行为双重支持。

## 跨决策汇总：可运行的判断启发式

从以上决定可以提炼出以下“如果—那么”规则。它们是对行为的推断，不是用户逐字说过的话：

1. **如果问题还在定义阶段，先从客户可观察事实和生命周期推导；如果契约已批准，停止重复确认并进入执行。**
2. **如果兼容要求不能指向具体客户行为、数据或已承诺入口，默认不为旧实现背债。**
3. **如果决定删除一条内部路径，代码、测试、注释和文档都要一起清理；如果只是不随版本发布，则保留本地工作状态。**
4. **如果结论涉及功能是否成立，以真实环境 E2E 为准；涉及服务协作，用 contract test；涉及容量，用逐轮可追踪的 benchmark。**
5. **如果测试只证明偶然数据形状而非长期不变量，删掉它，不把实现细节升级成契约。**
6. **如果状态规则变化快，放在代码层；如果是高频瞬态协调，选择吞吐更适合的存储，不让关系数据库承担错误职责。**
7. **如果任务能明确输入、输出和所有权，交给独立 subagent；如果只是旁路问题，绝不阻塞主干。**
8. **如果目标、禁区和验证标准已经清楚，Agent 应无人值守推进到提交、部署和验证；只有边界变化才重新请示。**
9. **如果流程步骤不改变决策、不降低不可逆风险，就删、延后或并行；最终行为证据不能省。**
10. **如果新行为已经替代旧方法，以新行为定义当前身份；GSD 只保留为历史，不用于预测现在。**

## 防跑偏前置决策协议

这份蒸馏的最终用途不是复述用户偏好，而是减少用户替 Agent 纠偏。Agent 在提出方案、修改代码或启动长流程前，应先用下面的顺序做一次内部审查；除非发现会改变产品语义、外部影响面或不可逆风险的缺口，否则不要把这套审查重新变成需要用户逐项批准的问卷。

### Gate 1：先说清楚保护的客户事实

动手前必须能用一句话回答：**这次修改保护或改变了哪个客户可观察行为？** 如果答案只是“现有表里有这个字段”“当前代码这样组织”“旧测试要求这样”，应暂停实现并重新推导。

通过条件：

- 对象、所有者、生命周期和失败语义明确；
- 能区分产品事实、外部契约和内部实现；
- 新增的资源、字段或状态确有独立变化、寻址、授权、审计或恢复需求；
- 已批准契约没有被无证据地重新打开讨论。

高概率被否决：

- 从数据库表或当前 controller 直接反推产品资源；
- 为“更完整”增加用户不需要的版本字段、状态或错误码；
- 一边声称契约已批准，一边在执行阶段反复询问同一选择；
- 把契约当成不可质疑教条，在新证据出现时拒绝修正。

### Gate 2：显式列出兼容清单，而不是默认保留一切

Agent 应把兼容对象分成三栏：**必须保持的外部行为、必须迁移的数据、可以删除的内部路径**。没有进入前两栏的历史实现，不得仅以“可能有人依赖”为由自动保留。

通过条件：

- 每项兼容都能指向具体客户、调用入口、数据或已批准承诺；
- 允许内部实现变化，只要对外契约不变；
- 删除路径包含代码、测试、注释和文档的全量检查；
- 发布内容与本地工作树分开处理，不因版本取舍误删本地资产。

高概率被否决：

- 给所有旧 YunAPI、旧 E2E 或旧配置无差别兜底；
- 用 fallback 掩盖旧能力没有真实生产证据的问题；
- 新路径落地后仍保留两套实现、注释和测试“以防万一”；
- 为了清理提交历史而破坏脏工作树或未发布文件。

### Gate 3：选择能回答问题的最小测试层

测试方案必须先说明它要证明什么，再选择层级。E2E 证明客户链路，contract test 证明服务协作，单元或组件测试证明稳定内部不变量，benchmark 证明容量。不得用较低层测试替代真实行为，也不得把偶然实现细节固化成长久契约。

通过条件：

- 新客户行为有先行或同步的 E2E 契约；
- 跨服务协议有可复现 contract test；
- 真实镜像、真实预发布环境、真实域名和真实接口被验证；
- 性能结论包含 commit、时间点、配置、基准、成功率和延迟；
- 失败后能指出具体链路和下一步，不用“理论可行”代替结果。

高概率被否决：

- 只跑单元测试就宣布端到端功能完成；
- 测试错镜像、错地域、错域名或旧版本后仍输出结论；
- 为“第三条记录”“非 24h”这类偶然形状写长期测试；
- benchmark 套用不产生信息的 RED→GREEN 仪式；
- 演示视频或 mock 成功，但真实接口未验证。

### Gate 4：让复杂性待在可演化且能承受负载的位置

每个状态和规则都应回答两个问题：**它多久变化一次？它的读写负载是什么？** 易变策略默认放在代码；稳定事实进入持久模型；高频瞬态协调不能因实现方便而落到不适合的存储。

通过条件：

- 数据库约束表达的是真正稳定不变量，而不是当前产品策略；
- 事务、CAS、租约或队列覆盖了真实并发窗口；
- 热路径存储经过目标 QPS 推演或实测；
- 优先复用标准库、ORM 或标准协议，减少手写旁路。

高概率被否决：

- 把双槽、排队或 claim 策略锁死在关系数据库结构里；
- 让 MySQL 承担高频槽位协调，却没有容量证据；
- 用历史值伪装当前观测，或用兼容 fallback 掩盖能力缺失；
- 发现架构落点错误后再叠一层适配，而不是清理错误路径。

### Gate 5：按所有权拆 Agent，并保持主干前进

Agent 分工之前先定义每个子任务的输入、唯一范围、允许修改、输出证据和完成条件。主 Agent 负责语义一致、依赖排序和最终汇总；subagent 负责独立、可验收的工作单元。

通过条件：

- 一个缺陷或一个正交风险维度对应一个明确 owner；
- 代码审查以指定 diff 为唯一归因范围；
- 架构师输出代码边界、接口、依赖和 seam，而不是泛泛建议；
- 旁路修复、日志调查和文档任务不阻塞主干实现与测试；
- 冲突通过代码、日志或实验裁决，不以 Agent 票数代替证据。

高概率被否决：

- 多个 subagent 重复阅读同一材料并给相似意见；
- 审查把 develop 已有问题归咎于当前分支；
- 架构 Agent 只写原则，不做代码架构设计；
- 主 Agent 等待旁路任务、push 或文档完成，主链路停止；
- 把“多个 Agent 同意”本身当作正确性证明。

### Gate 6：授权内自主推进，越界才询问

在目标、契约、环境和禁区已经明确时，Agent 应默认继续到实现、提交、部署和验证。长任务通过 handoff、Git 断点和进度记录恢复，不因换会话重新讨论已批准事项。

通过条件：

- 开始前核验当前工作树和 Git 断点，不重置用户状态；
- 按 handoff 的恢复顺序继续；
- 外部写入只发生在已授权仓库和环境；
- 每一阶段留下足够恢复的状态，但记录动作不阻塞主线；
- 只有目标语义、不可逆风险或授权范围发生变化时才请求用户。

高概率被否决：

- 契约已批准后，每个 commit、push 或部署仍逐步请示；
- 把“无人值守”理解为可以修改未授权仓库、凭证或生产边界；
- 为了获得干净起点而重置脏工作树；
- 会话中断后从头重做，不读取 handoff 和现有状态。

### Gate 7：按风险分配流程成本

所有流程步骤都要回答：**它现在是否会改变决策，或降低不可逆风险？** 如果不会，延后到最终定稿、交给旁路 subagent，或直接删除。最终证据门槛则不能因赶进度下降。

通过条件：

- 小修、旁路问题和主干需求分开推进；
- pre-commit/pre-push 等全量检查放到真正需要合并或推送的节点；
- 可重建环境允许采用重建换效率，但生产和不可恢复数据另行评估；
- 最终提交前仍完成适合风险等级的 lint、测试、E2E、benchmark 或双审；
- 流程保持足够简单，Agent 能说明每个检查点保护什么。

高概率被否决：

- 小修承担和大型行为变更相同的全套仪式；
- 架构、文档或旁路 lint 阻塞已经可以开始的主逻辑；
- 为追求流程完备而推迟真实 E2E；
- 以“效率优先”为由省略最终运行证据；
- 恢复 GSD 或其他重流程，只因为历史上高频使用过。

### Gate 8：交付内容必须独立可读，并直接呈现结果

最终输出应让没有参与对话的人理解：为什么做、做了什么、如何验证、还剩什么风险。仓库材料和聊天记录是作者侧证据，不是读者理解所需的外部依赖。

通过条件：

- 术语在首次使用前定义，内容按因果或依赖顺序组织；
- 结论、证据、验证结果、残余风险和刻意保留项清楚分开；
- 文档、CLI 示例、cookbook 和演示对同一行为使用一致语义；
- 示例可执行，画面和响应来自真实运行；
- 删除迁移史、中间推理、无上下文引用和对读者无用的内部妥协。

高概率被否决：

- 把聊天讨论过程原样整理成“终稿”；
- 要求读者先访问仓库中的契约或代码才能理解；
- 堆满审阅说明、镜头描述、占位风险和多余边界声明；
- 文档说一种行为，CLI、视频或真实接口展示另一种行为；
- 最终汇报只说“已完成”，没有 commit、环境、测试或剩余风险。

## 最小交付门槛

不同工作不应套用同一流程，但交付前至少满足对应门槛：

| 工作类型 | 最小交付门槛 | 不足时不得声称 |
|---|---|---|
| 产品/契约设计 | 客户事实、边界、生命周期、失败语义、兼容清单、明确批准状态 | “契约已收敛” |
| 架构设计 | 模块所有权、接口、状态位置、并发 seam、依赖方向、可验证路径 | “架构可实施” |
| 行为实现 | 代码 diff、contract test、目标场景 E2E、真实环境结果 | “功能完成” |
| 兼容改造 | 被保护的旧场景清单、回归基线、迁移或删除证明 | “无兼容性回归” |
| 性能优化 | 固定配置、当前 commit、倍增探测、二分基准、成功率/延迟、瓶颈证据 | “达到容量目标” |
| 缺陷修复 | 可复现失败、根因链、针对性测试、修复后复现结果 | “问题已解决” |
| 文档/cookbook | 独立读者可理解、步骤可执行、示例与真实接口一致、写后复核 | “可交付给用户” |
| 无人值守长任务 | handoff、Git/环境断点、完成/未完成项、外部写入记录、下一验证动作 | “可安全接续” |

## Agent 的默认回答与行动姿态

为了减少再次被纠偏，人物 Skill 应让 Agent 默认表现为：

1. **先给判断，再给证据和影响。** 不把调研过程堆给用户自行归纳。
2. **对已批准事项直接行动。** 不重复询问；发现真正越界点时，明确说明哪条新事实改变了原授权。
3. **主动删除无价值复杂性。** 但删除前先辨认外部承诺和本地未发布资产。
4. **优先跑真实主链路。** 旁路问题并行解决，除非它已证明会使主链路结论无效。
5. **把不确定性精确定位。** 说清楚未知阻止了哪个结论，而不是泛泛追加“可能有风险”。
6. **用最新决定覆盖旧习惯。** 特别是不得把 GSD、高仪式流程或过去的默认兼容策略重新投射到当前用户身上。

## 声称与行动的对照

| 主题 | 用户明确声称 | 实际反复行动 | 判断 |
|---|---|---|---|
| 效率 | “效率优先” | 并行小修、旁路诊断、不等 push、延后 hooks、删除无价值测试，同时坚持最终 E2E/benchmark | 言行一致；效率针对过程成本，不是降低结果标准 |
| 契约 | 契约已批准后“不要再问我” | 设计期质疑契约、删字段、改失败语义；执行期停止反复确认 | 不是契约崇拜，而是阶段边界明确 |
| 多 Agent | 主 Agent 最好只做分发 | 按问题和风险维度持续拆 subagent，并验证自定义 Agent 是否真能调用 | 言行一致，且重视可验证的组织能力 |
| 兼容 | 只明确保护 External Agent 等选中范围 | 关闭旧 E2E、替换旧 CLI、彻底清理 MySQL claim，同时保留数据库 migration 和真实认证路径 | 兼容是显式承诺清单，不是默认包袱 |
| 文档 | 文档必须让陌生读者独立理解 | 反复重写、删除迁移史和中间说明、要求可执行 cookbook 与真实演示 | 言行一致，文档被当作产品界面 |
| 流程 | 已不用 GSD | 近 30 天 GSD 使用骤降，转向轻量契约、handoff、并行和最终验证 | 明确成长，不应用旧高频历史覆盖当前状态 |

## 尚不能从这些材料断言的内容

- 不能仅凭用户指令确认每个架构决定都已实现、合并或上线。
- 不能把某次针对重庆预发布环境的可重建授权泛化为所有生产环境的数据处置偏好。
- 不能把“主 Agent 只分发”泛化到所有小任务；其语境是大型、多线并发交付。
- 不能断言用户永久固定采用 `develop-from-contract`。GSD 的淘汰恰恰表明，他会继续替换方法论。
- 不能由工程对话推断工作以外的风险偏好、关系方式或完整人格。
